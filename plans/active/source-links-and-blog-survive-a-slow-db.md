# Source links and the blog survive a database that is slow to answer

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This document must be maintained in accordance with `plans/PLANS.md`.

## Purpose / Big Picture

docket.pub publishes city meeting records with every fact linked to the city's own document. Two places in the web process answer a reader without what the database would have given them, and say nothing about it. The line that starts the web service gives the web process two database limits it did not have before (a connection attempt gives up after 10 seconds, a statement is ended after 30; decision `0135`), so a database that is merely slow now reaches both places, where a request used to wait. That start line is merged and not yet deployed; this plan lands before the operator deploys it.

The first place is the source-link allowlist: the closed list of hosts a page may print a source link to, and the minutes page viewer may fetch from. Today, when its one query fails, the page is served for ten minutes with every source address outside six fixed domains refused, and nothing is logged. A page that answers 200 with a city's source link withheld is what the principle "Source or silence" in `docs/PRINCIPLES.md` exists to prevent. After this plan a failed or timed-out query writes a log line that names the error, the list the database last gave keeps being served (a city host allowed a moment ago is still allowed), the query is asked again 30 seconds later, and the six fixed domains stand alone only when no list has ever loaded in the process, which is logged as an error.

The second place is the blog. Today, when the database does not answer while the web process starts, the process starts with an empty blog for its whole life, with no log line, and only another deploy mends it. After this plan the failure writes an error-level log line that names the exception, and the next request to a blog address at least 30 seconds later loads the posts in that request, so `/blog` lists its posts again by itself once the database answers.

Neither change shows on a page while the database is well, so the observation that stands in for it is a set of tests that fail on today's tree and pass afterwards inside `./tools/verify`, two of them run against a local socket that accepts a connection and never answers, which is what a database that is slow to answer looks like to the web process. The documents are brought to match: rows `D207` and `D208` leave `docs/DEBT.md`, `docs/specs/operations.md` (Railway specifics) describes the new behaviour, and step 4 of row `D206` tells the operator what to read in the log in place of "deploy again". No session of this plan deploys anything or runs any command against production.

## Decision Log

- Decision: the allowlist keeps the last list the database gave and asks again 30 seconds after a failed attempt ended; the six fixed domains are served alone only when no list has loaded in the process.
  Rationale: the fixed set is the lossy choice: it withholds a city-host link the database had just allowed, on a page that answers 200. A kept list is never wider than what the database last said (it is exactly that list), and its only cost is that a city deactivated while the database is unreachable stays allowed until the database answers, with a log line at every failed try. Keeping the fixed set but for a shorter time was weighed and rejected: it still withholds links, only more briefly, and more often under a database that fails now and then. Thirty seconds was chosen because it is the statement limit: one attempt can hold one thread for at most 30 seconds (10 for a connection that is not accepted), so with the interval counted from the end of the attempt, at most one of the four threads is asking and for at most half the time; ten minutes is how long a new city waits, and it stays the interval after a read that succeeds.
  Date/Author: 2026-11-23, plan author.
- Decision: a caller that finds the list expired while another thread is already asking the database serves the list it has (the expired one, or after `invalidate_cache` the last one loaded) and does not wait; only a caller with nothing to serve waits.
  Rationale: today every caller waits on the lock while one thread asks. That cost 30 seconds once in ten minutes; with a 30-second retry it would be nearly constant under a database that ends every statement at its limit, and every page with a source link would wait for a query whose answer it does not need. A caller with nothing to serve (the first request of the process) still waits, because the alternative is the fixed set for a process whose database is well.
  Date/Author: 2026-11-23, plan author.
- Decision: `POST /admin/source-security/refresh` (`invalidate_cache`) still forces the next call to ask the database, and it does not discard the last list that loaded. A separate function, `forget_allowlist`, discards both and is called by tests only.
  Rationale: the operator presses refresh to see a new city at once. If the re-read then fails, discarding the kept list would turn a press of that button into the very failure this plan removes (the fixed set, links withheld). The other reading, that refresh is how a host is removed and so must discard, was weighed: removal is by setting the city inactive, the next successful read drops its host, and a failed read is logged, so the operator knows the removal has not taken. Tests need a clean state between cases, and the web suite leaves a list loaded from the test database in the module, which is why the full reset exists and why the test classes call it in set-up.
  Date/Author: 2026-11-23, plan author.
- Decision: the blog's posts are loaded again on a later request, not by failing the start. The retry runs before a request to any address of the blog blueprint, at most once per 30 seconds counted from the end of the last attempt, in one thread at a time; other threads serve the state the process has without waiting.
  Rationale: failing the start was weighed. The start line runs the migrations against the same database seconds before `create_app`, so a database that is down already stops the deploy there; what reaches the handler is a database that answered the migrations and is slow a moment later, and failing then takes the whole site down for a blog the site no longer links to. Fifty-four test files call `create_app()`, and tooling calls it without a database. Only the blog blueprint's routes read the state (seven reads in `src/docket/web/blog.py`, none elsewhere), so a hook on that blueprint costs every other page nothing.
  Date/Author: 2026-11-23, plan author.
- Decision: the blog retry does not tell a database error from any other. Every failure of the load is logged at error level with the exception's type and text (the first, at start, with its traceback) and tried again under the same 30-second bound.
  Rationale: a malformed post or authors file raises through the same handler. Telling the two apart was weighed (retry only `psycopg2.Error`, log anything else once and stop): it would have the web layer import the database driver, which nothing under `src/docket/web/` does, and a wrong classification leaves the blog empty for the life of the process, which is the defect being paid. The uniform rule cannot loop per request, because the bound is on time: at most two attempts a minute, and only while blog addresses are being asked for. A permanent error costs a re-read of the post files and one log line at that rate.

## Context and Orientation

This section describes the tree at commit `ece4e4d`, which is `origin/main` and the commit this plan's branch `plan/source-links-and-blog-survive-a-slow-db` was cut from. `plans/active/` held no other plan when this one was written, and `gh pr list --state open --json number,title,headRefName` printed `[]` and exited 0 on 2026-11-23.

The project is a Python 3.10 Flask application. `src/docket/web/` is the web layer: the application factory `create_app` in `src/docket/web/__init__.py`, routes, and Jinja templates. `src/docket/services/` is the service layer, which owns every database transaction; `ARCHITECTURE.md` says nothing under `src/docket/web/` may call `db()` or `db_cursor()` (the two functions of `src/docket/db.py` that open a PostgreSQL connection with the `psycopg2` driver) or execute SQL. `src/docket/blog/` loads markdown posts from `content/blog/`. Production runs the web layer under gunicorn, a Python web server, as one worker process with four threads, so up to four requests are answered at once and module-level state is shared between them.

### The start line and its two limits

`Dockerfile` (which production runs) and `Procfile` start the web service with `python -m docket.migrations.runner && exec gunicorn 'docket.web:create_app()' ... --workers 1 --threads 4 --env 'PGOPTIONS=-c statement_timeout=30000' --env PGCONNECT_TIMEOUT=10`. The two `--env` settings reach the web process only: PostgreSQL ends any statement of the site's after 30 seconds, and a connection attempt gives up after 10. Either raises `psycopg2.OperationalError` (or its subclass for a cancelled statement) in the code that asked. Decision `0135` (`docs/decisions/0135-the-web-service-is-one-gunicorn-worker-with-four-threads.md`) records the line; `tests/unit/test_web_start_line.py` pins it. The line is merged and not deployed; row `D206` in `docs/DEBT.md` holds the operator's five steps for the deploy and the readings after it. This plan changes neither file and none of `D206`'s steps but the tail of step 4.

### The source-link allowlist today

`src/docket/web/source_security.py` (274 lines) answers one question: is this address one a page may link to. `STATIC_ALLOWED_DOMAINS` is six fixed domains (`granicus.com`, `civicclerk.com`, `civicplus.com`, `youtube.com`, `youtu.be`, `vimeo.com`). `load_municipality_hosts(db_cursor_fn)` runs the module's one SQL statement,

    SELECT adapter_config->>'base_url' AS url FROM municipalities WHERE active = TRUE AND adapter_config ? 'base_url'

and returns the host of each address it gives, lower-cased, with port and user name stripped, skipping empty and malformed values. `build_allowlist(db_cursor_fn)` is the fixed set united with those hosts. `get_allowlist(db_cursor_fn=None)` keeps the result in the module global `_CACHE`, a pair of an expiry time (`time.time()` plus `_CACHE_TTL_SECONDS`, 600) and the list, under `_CACHE_LOCK`; its parameter defaults to `docket.db.db_cursor`, imported inside the function. When `build_allowlist` raises anything, the handler (`except Exception:`, lines 256 to 261) takes `STATIC_ALLOWED_DOMAINS`, stores it for the same 600 seconds, and logs nothing; the module has no logger. `invalidate_cache()` sets `_CACHE` to `None`. `is_url_safe(url, allowed_domains=None)` asks `get_allowlist()` when no list is passed; `is_viewer_url(url, allowed_domains=None)` is the stricter question for the minutes page viewer (https, no user name, no port but 443, no backslash or white space) and ends by asking `is_url_safe`.

Who asks. `create_app` registers `is_url_safe` as the Jinja global `is_source_url_safe` and `is_viewer_url` as `is_minutes_viewer_url`. Three templates call them: `src/docket/web/templates/meeting_detail.html` (lines 293 and 297), `src/docket/web/templates/partials/_vote_result_block.html` (lines 46 and 52), and `src/docket/web/templates/partials/source_anchor_button.html` (line 109), each printing a source link only on a yes. No template includes `source_anchor_button.html` (`grep -rn source_anchor_button src/docket/web/templates` lists only the partial itself); tests render it. One route asks directly: the minutes page viewer in `src/docket/web/public.py` (line 369) answers the site's 404 when `is_viewer_url` says no to the meeting's stored `minutes_url`, and otherwise the web process fetches that address. So a wider list would let the web process make a request it should not, and this plan's kept list is, by construction, exactly a list the database gave and never wider. `src/docket/web/admin.py` (`refresh_source_security`, line 412) is `POST /admin/source-security/refresh`, which calls `invalidate_cache()` and answers `Allowlist cache invalidated. Next request will refresh from DB.`

`tests/unit/test_source_security.py` (548 lines) holds the module's tests. It injects the database through a fake cursor: `_FakeCursor` and `_make_cursor_fn(rows)`, with rows shaped `[{"url": "https://newcity.example.gov"}]`, passed positionally to `load_municipality_hosts`, `build_allowlist` and `get_allowlist`. `TestAllowlistCache` pins today's failure behaviour in two tests, `test_db_failure_falls_back_to_static_allowlist` and `test_db_failure_caches_static_fallback_for_ttl`, and calls `invalidate_cache()` in `setup_method` and `teardown_method`, as does `TestRefreshSourceSecurityRoute`, whose `test_post_invalidates_cache` asserts `source_security._CACHE is None` after the POST. Four other test files (`tests/unit/test_smart_brevity_card_dispatcher.py`, `test_list_agenda_items.py`, `test_engagement_strip.py`, `test_source_anchor.py`) pass an explicit list to `is_url_safe` and never touch the cache; `tests/web/test_minutes_viewer.py` line 433 checks the Jinja global is `is_viewer_url`. ### M2: a failed allowlist query is logged, the loaded list is kept, and the retry is short

Goal: the behaviour of the first paragraph of Purpose, with `D207` deleted and the two specs saying what happens.

The contract, which Interfaces and Dependencies restates as names. The module gains a logger, a second piece of state `_LAST_LOADED` (the last list a successful read gave, the fixed set united with the hosts; `None` until a read succeeds in this process), a third, `_LAST_ATTEMPT_FAILED` (a bool, false until an attempt fails, true from a failed attempt until the next one that succeeds), and `_RETRY_SECONDS = 30`. `_CACHE` keeps its shape and meaning: `None`, or a pair of expiry and the list being served; the expiry is a `time.monotonic()` value, where today it is a `time.time()` one (Decision Log, 2026-11-23 revision). `get_allowlist` then behaves as follows. A list that has not expired is returned without the lock, as now. Otherwise the caller's value in hand is the expired list if `_CACHE` holds one, else `_LAST_LOADED`. A caller with a value in hand tries the lock without waiting and, if another thread holds it, returns the value in hand; a caller with none waits for the lock. The lock is released in a `finally` that begins straight after it was taken, so no path out of the function leaves it held. Under the lock it reads the clock again and checks again for an unexpired list (another thread may have just stored one, and a caller that waited may have waited ten seconds) and otherwise asks the database. On success it stores the list as `_LAST_LOADED` and in `_CACHE` with an expiry of `_CACHE_TTL_SECONDS` from now; if `_LAST_ATTEMPT_FAILED` is true it logs the recovery at warning level and sets it false, and a read that follows no failure (the first of the process, a ten-minute re-read, a refresh) logs nothing. On any exception it serves `_LAST_LOADED` when there is one, logging at warning level, and the fixed set when there is none, logging at error level, sets `_LAST_ATTEMPT_FAILED` true, and stores what it serves in `_CACHE` with an expiry of `_RETRY_SECONDS`. Both expiries are counted from `time.monotonic()` read after the attempt returned or raised, not from the time read on entry: an attempt can last 30 seconds, and an expiry counted from before it would already be past. `invalidate_cache()` sets `_CACHE` to `None` and leaves `_LAST_LOADED` and `_LAST_ATTEMPT_FAILED`, so a refresh pressed while the database is failing does not hide the recovery line. `forget_allowlist()` sets `_CACHE` and `_LAST_LOADED` to `None` and `_LAST_ATTEMPT_FAILED` to false. Each log line is one line; the two failure lines hold the exception's type name and its text, and the number of seconds to the next try:

    source allowlist: query failed (OperationalError: <text>); serving the last list that loaded (<n> hosts); next try in 30 s
    source allowlist: query failed (OperationalError: <text>); no list has loaded in this process, so only the fixed domains are allowed; next try in 30 s
    source allowlist: the database answered again (<n> hosts)

### M3: a start without the database is logged and the posts load on a later request

Goal: the behaviour of the second paragraph of Purpose, with `D208` deleted and `D206`'s step 4 and the spec telling the operator what to read.

The contract. `src/docket/web/blog.py` gains a logger, `BLOG_RETRY_SECONDS = 30`, and two things. `init_blog_state(app, *, content_root, authors_yaml)` makes the first attempt: it calls `_query.list_municipalities()` and `load_blog_state` exactly as `create_app` does today and stores the result as `app.config["BLOG_STATE"]`. If the attempt raises anything, it stores the empty `BlogState`, logs at error level with the traceback (`exc_info=True`), and stores under `app.config["BLOG_STATE_PENDING"]` an object that holds the load to repeat, a `threading.Lock`, the type of the exception the last attempt raised, and `next_try`, a `time.monotonic()` value `BLOG_RETRY_SECONDS` after the attempt ended. When the attempt succeeds the key is absent. `create_app` calls `init_blog_state` in place of its `try` block. The second is a `before_request` function on the blueprint: it returns at once when the request is for the asset route (`request.endpoint == "blog.asset"`), which reads no post and must not wait up to the connection limit for a read it does not use; it returns at once when `current_app.config.get("BLOG_STATE_PENDING")` is `None` (always so for an application that loaded at start, and for a bare application that never called `init_blog_state`) or when `time.monotonic()` is before `next_try`; otherwise it tries the lock without waiting and returns if another thread holds it; holding it, it checks the two conditions again and repeats the load. The check under the lock reads the key from `current_app.config` again and returns unless the value is the very object whose lock it holds (`is`), and only then compares the clock: a thread that read the key just before another thread finished loading holds a reference to an object that is no longer pending, and comparing that object's `next_try` alone would load the posts a second time and log the recovery twice. On success it stores the state under `app.config["BLOG_STATE"]`, then removes the pending key, both before the lock is released (in a `finally`), and logs at warning level. On any exception it logs at error level and sets `next_try` to `BLOG_RETRY_SECONDS` after that attempt ended; the line carries the traceback (`exc_info=True`) only when the exception's type differs from the one the attempt before it raised, so a database that stays down prints one line a try and an error of a new kind (a malformed post met once the database answers) is printed in full once. The function never raises and never returns a response, so the request goes on to its route and reads whatever state the process then has. The lines:

    blog: posts not loaded when the process started (OperationalError: <text>); the blog is empty until a later request loads them; next try in 30 s
    blog: posts not loaded on a later request (OperationalError: <text>); next try in 30 s
    blog: posts loaded on a later request (<n> posts)

The request that repeats the load waits for it (up to the connection limit, 10 seconds on production, when the database is still not answering) and, when it succeeds, is itself answered with the posts. The seven reads of `current_app.config["BLOG_STATE"]` are not edited.
