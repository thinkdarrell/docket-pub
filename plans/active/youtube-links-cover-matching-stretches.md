# YouTube links cover the matching stretches: a recording that matches its Granicus clip at two offsets, or that one conflict window rejected, stores one row per confirmed stretch and links inside each stretch open YouTube

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This document must be maintained in accordance with `plans/PLANS.md`.

## Purpose / Big Picture

docket.pub links from a Birmingham agenda item, a vote, a transcript marker, and a minutes-versus-video row into the meeting's video. Since 2026-11-06 such a link opens the council's YouTube recording at the right second when the transcriber has measured where that recording sits on the Granicus clip's clock, and opens the Granicus player at the item's chapter otherwise. The matcher that measures a recording gives one verdict for the whole of it. On the production read of 2026-11-12 (`docs/runbooks/transcripts.md`, History), 171 of the 359 attached recordings had been measured: 108 passed, 60 were rejected, 3 failed. About 33 of the 60 are recordings that match the clip at two offsets, a stream that dropped and resumed or two pieces stitched together, which the matcher rejects whole as `conflict` or `windows` (meeting 2387: score 118.1, runner-up 67.8; meetings 157 to 168 of early 2023, all with the same shape). About 12 more are strong single matches that one strong window at another offset, or the 60 percent window share, threw out (meeting 2238: 34 of 40 windows agree, score 158.9, runner-up 4.7). Every link of those 45 meetings opens Granicus, often at the start of a two-hour recording, although the recording holds the moment. That is debt row `D98`, whose trigger has fired.

After this plan the matcher stores coverage in pieces. A recording gets one `meeting_video_alignments` row per confirmed stretch, each with its own offset and its own span of the Granicus clock, and the pass mark of decision `0078` (score, margin, window share, no conflict) is applied to each stretch instead of to the recording. A window that matches strongly at another offset ends a stretch instead of rejecting the recording. The link builder in `src/docket/services/video_links.py` opens YouTube for any second a passing stretch covers, trying the primary recording's stretches first and then the others by where they start, and opens Granicus for a second that falls between stretches. The method version rises from 2 to 3, but the 108 passed rows are not measured again: the transcriber keeps a passed row trusted from version 2 up (a floor), as the site already does (`MIN_METHOD_VERSION` stays 2), and migration 046 deletes only the 60 rows rejected at version 2, so the second pass costs about 60 downloads instead of 171 (`D110`). The one row passed by hand, meeting 15's row 832 with reason `operator`, is a passed row at version 2 and survives untouched as a single stretch.

An outside reader can see it in four places once the operator has deployed, granted, rebuilt the transcriber image, and run the backlog (the steps under Validation and Acceptance, which no factory session can take). First, before any new measuring, the third statement of query 4 in `plans/completed/video-links-land-on-the-moment.md` prints no `rejected` row and still prints the `passed` rows at version 2. Second, after the backlog run, the second statement of that query shows, for meeting 2387 or one of meetings 157 to 168, two or more `passed` rows at version 3 for one `meeting_video_id` with different offsets and spans that do not overlap, and for meeting 2238 at least one `passed` row covering the windows that agreed; a recording with no confirmed stretch, the 8 wrong-video rows of issue #174 among them, comes back as one `rejected` row at version 3 and is not a candidate again. Third, in a browser, an agenda item of meeting 2238 whose cue point lies inside a stored stretch has a "Watch this vote on YouTube ↗" link that opens the recording at the cue's second minus that stretch's offset, and an item whose cue point falls between two stretches reads "on Granicus" and opens its chapter; the transcript page's item links and the minutes-versus-video rows follow, because they build through the same module. Fourth, in this worktree, `./tools/verify` passes with the tests this plan names.

## Decision Log

- Decision: coverage is found per offset from the windows the recording already has, not by re-measuring the remainder of the recording after each stretch. Candidate offsets are the whole-recording peak and then the best offset of every window that matches strongly (at or above `CONFLICT_SCORE`) somewhere else, strongest first, merged within `AGREE_S`, at most `MAX_OFFSETS` (4). For each candidate, every counted window is classed `conflict` (its best match anywhere is strong and more than `AGREE_S` from the candidate), else `agree` (its best match within `LOCAL_SEARCH_S` of the candidate lies within `AGREE_S` of it), else `quiet`; a stretch is a maximal run of counted windows with no conflict in it, trimmed to its first and last agreeing window; a stretch's score is the whole-recording cross-correlation at the candidate's lag; the runner-up is the best score more than `RUNNER_EXCLUDE_S` from every candidate that produced a stretch meeting the window share with a confirmed span (and from the whole-recording peak alone when none did); the pass mark is `verdict(score, runner_up, counted, agreed, 0)` per stretch and the pieces of decision `0081` trim each stretch's ends.
  Rationale: every number this computes for a single-offset recording with no conflict window is the number the module computes today (the run is all counted windows trimmed to the first and last agreeing one, the candidate set is the peak alone, the runner-up excludes the same 5 seconds), which is how the labelled table's verdicts and the nine pairs' offsets, scores, and coverage are kept without the labelled audio, which is gone. The window cross-correlations are computed once and reused for every candidate, so the cost is the same downloads and nearly the same arithmetic. The alternative, cross-correlating the unexplained remainder again after each stretch, gives cleaner scores for a short second part but changes the figures of every recording that has any conflict window and could not be checked against the table either. A second part's score being the whole-recording correlation at its lag is a deliberate guard: one window that matches strongly elsewhere (the shape that rejected meeting 2238) lifts no peak to 9 in a two-hour recording, so it ends the stretch and is not stored as one; the prototype's 155-second second part failed the same way.
  Date/Author: 2026-11-12, the plan author (Claude), from the operator's goal and the prototype in Artifacts and Notes.

- Decision: `ALIGN_METHOD_VERSION` becomes 3 and a new constant `ALIGN_TRUSTED_VERSION = 2` in `transcriber/transcriber/align.py` is the floor from which a `passed` row stays trusted by the transcriber's candidate query; `MIN_METHOD_VERSION` in `src/docket/services/video_links.py` stays 2; a `rejected` row below the current version is a candidate, a `passed` row below the trusted floor is a candidate, and a `passed` row at or above the floor is not.
  Rationale: the operator's goal bounds the cost of the bump to the rows the change can improve. A passed row at version 2 was a single-offset recording whose windows agreed and whose ends the pieces checked; the stretch rule gives it the same row. The two constants state the same fact in two processes that share no code (the transcriber image does not import `docket`), as `ALIGN_METHOD_VERSION` and `MIN_METHOD_VERSION` already do, and each comment names the other. The candidate query is the only place the trusted floor is read besides the site, so the floor is a parameter of `alignment_candidates` and `alignment_backlog`, not a hidden constant inside the SQL.
  Date/Author: 2026-11-12, the plan author, from the goal.

## Context and Orientation

This section describes the repository as it stood on 2026-11-12 on branch `plan/youtube-links-cover-matching-stretches`, cut from `origin/main` at commit `0f5b61c` and rebased on 2026-11-15 onto `5560ac3`, in the worktree `.claude/worktrees/youtube-links-cover-matching-stretches` with its own `venv/`. ### The terms this plan uses

Granicus is the vendor whose site, https://bhamal.granicus.com, holds Birmingham's meeting videos; a clip is one Granicus recording, and a meeting row whose `meetings.external_id` is all digits is such a clip, with its player page `MediaPlayer.php?view_id=2&clip_id=<id>` stored as `meetings.video_url`. The Granicus clock is seconds from the start of the clip; an agenda item's cue point (`agenda_items.video_timestamp_seconds`), a vote read off the video (`votes.video_timestamp`), and a transcript segment are all on it. A chapter id is the id of a cue point; the Granicus player can jump only to a chapter (`&meta_id=<id>`). A YouTube recording is a video on the council's channel attached to a meeting as a row of `meeting_videos` (`id`, `meeting_id`, `provider`, `video_id`, `is_primary`, and more); a meeting can have several.

The offset of a recording is Granicus seconds minus YouTube seconds for the same instant, so a moment at Granicus second g is at YouTube second g minus the offset. Coverage is a stretch of the Granicus clock a recording has been confirmed to show. A measurement is what the transcriber stores about one recording against one clip. The method version is an integer the matcher stamps on every row so a changed method can tell old rows from new. The pass mark is the rule that decides `passed` or `rejected`. A stretch, this plan's term, is one contiguous run of a recording that matches the clip at one offset: it has an offset, a coverage, and the figures its pass mark was reached on. A window is a 300-second piece of the YouTube recording the matcher checks on its own; a piece is a 60-second part of a window used to find where coverage begins and ends.

The transcriber is the package under `transcriber/`, run on the operator's Legion desktop in Docker; `ARCHITECTURE.md` calls it the fourth process. It connects to the production database as the PostgreSQL role `transcriber`, whose grants are the file `scripts/sql/create_transcriber_role.sql`. The measuring pass is the part of an ordinary transcriber run that measures attached recordings before the speech model loads (`transcriber/transcriber/measure.py`). numpy is the array library the matcher uses; it is in the repository's `venv/` and in the transcriber image. A migration is a numbered module under `src/docket/migrations/` listed in `MIGRATIONS` in `runner.py`; `apply_migrations` runs each unapplied one in list order and records its number in `schema_migrations`, and `rollback_migration(conn, n)` runs one module's `SQL_DOWN` and forgets its number. A migration that is still recorded as applied is skipped by the next `apply_migrations`, which is why a test that rolls back migration 042 must roll back 045 first (below).

### The matcher as it stands

`transcriber/transcriber/align.py` is a pure module (standard library and numpy) whose docstring explains the method. `features(samples)` turns 8 kHz 16-bit audio into four smoothed log band-energy envelopes at `FPS` (25) frames a second. `xcorr_z(a, b)` returns the z-scored cross-correlation of two feature arrays and the offset each entry stands for. `measure(granicus, youtube)` does the rest: the whole-recording cross-correlation gives the offset (its highest peak), the score (that peak's z), and the runner-up (the best z more than `RUNNER_EXCLUDE_S`, 5 seconds, from the offset); the recording is cut into windows of `WINDOW_S` (300 seconds) from its start plus one end window that ends where the overlap of the two recordings ends; a window is counted when it lies inside the clip under the offset, confirms when its best match within `LOCAL_SEARCH_S` (40 seconds) of the offset lies within `AGREE_S` (2 seconds) of it, and is a conflict when its best match anywhere has z at least `CONFLICT_SCORE` (8.0) and lies more than `AGREE_S` from the offset. `verdict(score, runner_up, windows, confirmed, conflicts)` is the pass mark in order: `no_window` for no counted window, `score` under `PASS_SCORE` (9.0), `margin` under `PASS_MARGIN` (4.0) over the runner-up, `windows` under `PASS_WINDOW_SHARE` (0.6) of counted windows confirming, `conflict` for any conflict, else `passed`. Coverage is `confirmed_span(g, y, offset, start_s, end_s)` over the span from the first confirmed window to the end of the last: it walks inward from each end in pieces of `EDGE_S` (60 seconds) until a piece confirms by the window's test, and returns None when none does, in which case a recording that met the mark is rejected as `edges`. The result is the frozen dataclass `Measurement(status, reason, offset_s, granicus_start_s, granicus_end_s, score, runner_up, windows, windows_confirmed)`; `describe(m)` is the one-line form the pass logs; `measure_files` and `main` read two WAV files. `ALIGN_METHOD_VERSION = 2`.

The constants are the method: the pass mark was chosen on 72 labelled pairs of real recordings (decision `0078`; the table is in `plans/completed/video-links-land-on-the-moment.md`, Artifacts and Notes, and the nine matched rows are copied into `test_verdict_reproduces_the_labelled_table`). ## Idempotence and Recovery

Migration 046 can be applied once and rolled back: its up uses `ADD COLUMN IF NOT EXISTS` and `DROP CONSTRAINT IF EXISTS` before each `ADD CONSTRAINT`, and its `DELETE` is harmless to repeat; its down deletes rows with `stretch > 1` (the second and later stretches of recordings measured at version 3, which the next transcriber run makes again once the migration is re-applied) and restores the single-column key; the rejected rows it deleted on the way up are not restored and are re-measured by the next run instead. `tools/test-db` rebuilds the throwaway database at any time and `tools/test-db --drop` removes it.

The measuring pass can be run any number of times: a recording with a current row (passed at the floor or later, rejected at the current version, failed within seven days) is not a candidate, a save deletes and inserts the recording's rows in one transaction and commits on its own, and the work files are deleted in `finally` blocks. To measure one recording again the owner deletes its rows; to measure every rejected recording again the version rises. The off switch (`UPDATE meeting_video_alignments SET status = 'rejected', reason = 'operator' WHERE status = 'passed'`) and its restore (`... SET status = 'passed', reason = NULL WHERE reason = 'operator'`) touch every stretch row and still work; the restore also turns row 832 back into an ordinary passed row, so an operator who wants that row to keep its reason restores with `WHERE reason = 'operator' AND meeting_video_id <> 832`.

An old transcriber image against the new table, or the new image against the old table, measures nothing and transcribes as before: the save fails, the pass logs `measure: skipped (...)`, and no row changes. The order of the operator's steps avoids both.

The link builder writes nothing. A wrong link is corrected by deleting the measurement behind it.

A milestone that will not fit is split in place in Progress (completed: X; remaining: Y) with a Decision Log entry, and the session stops.

### The reference arithmetic

The body of `measure` as the prototype computed the figures in Surprises & Discoveries on 2026-11-12, against the module's `xcorr_z`, `verdict`, `confirmed_span`, and constants as they stand. M1 writes this into `align.py` with the `Stretch` and `Measurement` construction, the rejected reason, and `describe` around it; the arithmetic itself is not to be changed, because the figures above were produced by it.

    gdur = len(g) / FPS
    z, lags = xcorr_z(g, y)
    k = int(np.argmax(z)); o1 = float(lags[k]); s1 = float(z[k])
    wl = int(WINDOW_S * FPS)
    grid = list(range(0, len(y) - wl + 1, wl))
    cache = {}
    def win(s):                       # one window's cross-correlation, lags on the recording's clock
        if s not in cache:
            wz, wlags = xcorr_z(g, y[s:s + wl]); cache[s] = (wz, wlags - s / FPS)
        return cache[s]
    def starts_for(o):                # the grid plus this offset's end window
        st = list(grid)
        last = min(len(y), int(round((gdur - o) * FPS))) - wl
        if last > 0 and last not in st: st.append(last)
        return sorted(st)
    cands = [o1]; strong = []
    for s in starts_for(o1):
        wz, wlags = win(s); kb = int(np.argmax(wz))
        if wz[kb] >= CONFLICT_SCORE: strong.append((float(wz[kb]), float(wlags[kb])))
    for sc, off in sorted(strong, reverse=True):
        if all(abs(off - c) > AGREE_S for c in cands) and len(cands) < MAX_OFFSETS:
            cands.append(off)
    def z_at(o): return float(z[int(np.argmin(np.abs(lags - o)))])
    def classify(o):                  # [(window start in YouTube seconds, 'conflict' | 'agree' | 'quiet')]
        rows = []
        for s in starts_for(o):
            ys = s / FPS
            if o + ys < 0 or o + ys + WINDOW_S > gdur + 1e-6: continue
            wz, wlags = win(s); kb = int(np.argmax(wz))
            near = np.abs(wlags - o) <= LOCAL_SEARCH_S
            kn = int(np.argmax(np.where(near, wz, -np.inf)))
            if wz[kb] >= CONFLICT_SCORE and abs(wlags[kb] - o) > AGREE_S: kind = 'conflict'
            elif abs(wlags[kn] - o) <= AGREE_S: kind = 'agree'
            else: kind = 'quiet'
            rows.append((ys, kind))
        return rows
    def runs(rows):                   # cut at conflicts, trimmed to the first and last agreeing window
        out = []; cur = []
        for ys, kind in rows:
            if kind == 'conflict':
                if cur: out.append(cur); cur = []
            else: cur.append((ys, kind))
        if cur: out.append(cur)
        trimmed = []
        for r in out:
            idx = [i for i, (ys, k) in enumerate(r) if k == 'agree']
            if idx: trimmed.append(r[idx[0]:idx[-1] + 1])
        return trimmed
    found = []                        # (offset, counted, agreed, span in YouTube seconds)
    for o in cands:
        for r in runs(classify(o)):
            counted = len(r); agreed = sum(1 for _, k in r if k == 'agree')
            if agreed / counted < PASS_WINDOW_SHARE: continue
            span = confirmed_span(g, y, o, r[0][0], r[-1][0] + WINDOW_S)
            if span is None: continue
            found.append((o, counted, agreed, span))
    confirmed_offsets = sorted({o for o, _, _, _ in found})
    rest = z.copy()
    for o in (confirmed_offsets or [o1]):
        rest[np.abs(lags - o) <= RUNNER_EXCLUDE_S] = -np.inf
    runner = float(rest.max())
    stretches = []
    for o, counted, agreed, span in found:
        status, reason = verdict(z_at(o), runner, counted, agreed, 0)
        if status == 'passed':
            stretches.append(Stretch(offset_s=o, granicus_start_s=max(0.0, o + span[0]),
                                     granicus_end_s=min(gdur, o + span[1]), score=z_at(o),
                                     runner_up=runner, windows=counted, windows_confirmed=agreed))
    stretches.sort(key=lambda t: (t.granicus_start_s, t.offset_s))

The whole-recording figures for the `Measurement` are `o1`, `s1`, `runner`, and the counts over `classify(o1)` (counted is its length, confirmed its `agree` entries).
