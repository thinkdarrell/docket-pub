# Keep the old transcript public through a meeting-id re-run and restore the row when the re-run fails

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This document must be maintained in accordance with `plans/PLANS.md`.

## Purpose / Big Picture

docket.pub publishes machine transcripts of Birmingham City Council meetings at `/al/birmingham/meetings/<id>/transcript/`. A desktop program called the producer (the `transcriber/` package, run on a GPU machine the operator calls the Legion) transcribes the video and uploads the segments; the Railway worker then resolves speaker names, extracts events, and compares the transcript against the minutes. Since 2026-10 the operator can re-transcribe one meeting with `python -m transcriber.cli --meeting-id N`, which re-claims the meeting's existing `transcripts` row in place (decision `0048`). The closing review of the plan that built that path (`plans/completed/transcriber-clean-speaker-segments.md`, pull request 121) found five things wrong with it, recorded as `D55` in `docs/DEBT.md`, and this plan fixes all five.

After this work, a reader who is looking at a meeting's transcript while the operator re-runs it keeps seeing it. The moment the operator runs `--meeting-id N`, the row's status goes back to `claimed`, and today that makes the transcript page a 404, removes the meeting page's transcript link, empties the item excerpts and the search hits, and stays that way for the hour or so the audio download and GPU transcription take; if the re-run ends `low_speech` the page is gone for good, and if it ends `failed` the old transcript comes back under status `failed` and lands in the admin held tab, from which a retry restarts the worker on the old events and discards the `transcript_changed` marker. After this work the page, the link, the excerpts, and the search hits serve the version-1 turns at every step until the new upload replaces the segments (that replacement is already one transaction), and a re-run that ends `failed` or `low_speech` puts the row back exactly as it was before the claim, column for column, so the Railway side never sees a producer-failed row with `uploaded_at` set and the held tab never lists one. The failure is still recorded, in the producer's log line, its exit code, and `producer_heartbeats.last_status`.

Three smaller corrections ride along, each from the same review. `--meeting-id` exits 1 whenever its `done` line's `uploaded` count is 0 (today it exits 1 only when every count is zero, so a run that claimed the meeting and then failed exits 0, and the spec says it exits 1). The producer's own status writes stop stamping `last_attempted_at`, so the 30-minute busy guard reads only the worker's claim stamp, as its docstring, the README, the spec, and the runbook already claim (today a second `--meeting-id` right after a failed re-run is refused with a message blaming the worker). And the producer `__version__` goes to `0.2.1` so the heartbeat table shows which producer code ran; `TRANSCRIPT_VERSION` stays 2 because the uploaded output is unchanged.

The fifth finding, a stale "ten database tests" count in `docs/specs/operations.md`, was already corrected on `main` at that plan's retrospective: `grep -n "ten database tests" docs/specs/operations.md` printed nothing on this branch on 2026-10-16, and line 47 names `transcriber/tests/test_db.py` without a count. This plan confirms that by grep in M3 and changes nothing there.

How to see it working, on a disposable database (every command in this plan runs from the worktree root, `/home/thinkdarrell/docket-pub/.claude/worktrees/rerun-keeps-transcript-public`, with that checkout's own `venv/`): the probe in Artifacts and Notes walks one row through `claim_next`, `upload`, `claim_meeting`, `audio_fetched`, `transcribed`, and a restore, printing whether the public predicate returns the row at each step. On 2026-10-16, before any work, it printed `public: None` after `claim_meeting`, `audio_fetched`, and `transcribed`, and `MeetingBusy` on the second `claim_meeting`; after M2 it prints a public row at every step and `claimed` on the second claim. The test counts move from `621 passed` to `623 passed` in the integration tier (two new tests) and from `62 passed` to `68 passed` in the producer suite (six new tests), and `./tools/verify` ends `verify: all 5 checks passed` at every milestone (it printed `all 5 checks passed in 94s.` on this branch before any work).

## Decision Log

- Decision: the public predicate becomes `uploaded_at IS NOT NULL AND status <> 'low_speech'`, and `PUBLIC_STATUSES` is deleted rather than kept beside it.
  Rationale: the brief rejected a new status value such as `retranscribing` because it needs a migration altering the CHECK in `src/docket/migrations/035_transcripts.py` and a change at every reader of `status`; keying on `uploaded_at` needs neither and leaves the producer's status transitions as the claim mechanism. `uploaded_at` is written only by `upload()` and never cleared, so it is exactly "segments have been published". `low_speech` is excluded because both writers of it (`is_low_speech()` in the producer, `mark_low_speech()` in the worker's fitness gate) mean "there is no usable transcript here", and `test_fitness_gate_moves_mic_check_to_low_speech_without_llm` asserts that a worker `low_speech` on an uploaded row hides it. `PUBLIC_STATUSES` has no reader outside `src/docket/services/transcripts.py` (grep over `src`, `tests`, `scripts` on 2026-10-16), and keeping an unused tuple beside the rule would be a second owner of the fact `docs/PRINCIPLES.md` forbids.
  Date/Author: 2026-10-16, plan author.
- Decision: a failed or `low_speech` re-run of an uploaded meeting is undone from an in-memory snapshot of the row that `claim_meeting()` reads before its UPDATE and returns on the `Claim` as `prior`; `restore_row()` writes every column of that snapshot back except `id` and `meeting_id`.
  Rationale: nothing else can restore the row. The pre-claim status may be any worker status and the claim resets five other columns, so "set status back to uploaded" would be wrong for a `compared` or `needs_review` row; there is no column to park a snapshot in, and the `transcriber` role cannot add one (`scripts/sql/create_transcriber_role.sql` grants only `SELECT, INSERT, UPDATE, DELETE` on the four producer tables, which is also why `restore_row()` may write every column). Writing every column, `updated_at` and the unchanged `uploaded_at` included, is what makes the acceptance literal: `SELECT *` before the claim and after the failure print the same row. The snapshot is current for the whole run because nothing else can write the row in that window: the worker's `CLAIM_SQL` takes only `uploaded`, `speakers_resolved`, and `events_extracted` rows and the producer holds the row at `claimed`, `audio_fetched`, or `transcribed`; `retry_transcript()` takes only `needs_review` and `failed`. The one hole is a producer that dies mid-run (power loss): the snapshot dies with it, and the next run of that meeting ends as a first run would; Context and Orientation and the spec say so.
  Date/Author: 2026-10-16, plan author.

## Context and Orientation

The repository is a Python 3.10 Flask application with a PostgreSQL database. Three things in it matter here.

The producer is the package under `transcriber/` (its own `pytest.ini`, its own tests under `transcriber/tests/`, run by `./tools/verify` as its fifth check with the root `venv/bin/python`). It connects to Postgres as the `transcriber` role, which may read `meetings`, `municipalities`, `council_members`, and `agenda_items` and may `SELECT, INSERT, UPDATE, DELETE` on `transcripts`, `transcript_segments`, `transcript_speakers`, and `producer_heartbeats` (`scripts/sql/create_transcriber_role.sql`). `transcriber/transcriber/db.py` holds its database layer: `claim_next()` picks the newest eligible meeting under an advisory lock and inserts or re-claims a `transcripts` row at `claimed`; `claim_meeting()` serves `--meeting-id N` by setting that meeting's existing row back to `claimed` (or inserting one), resetting `stage_attempts`, `last_attempted_at`, `needs_review_reason`, and `last_error`, and writing `compare_skipped_reason = 'transcript_changed'` when the row had been uploaded (`uploaded_at IS NOT NULL`), after refusing with `MeetingBusy` any row whose `last_attempted_at` is within the last 30 minutes (`_MEETING_SQL`'s `busy` column); `mark_status()` writes a status plus optional columns from `_UPDATABLE` and today also `last_attempted_at = now()` on every call (line 158); `upload()` deletes the meeting's segments, upserts speakers, copies the new segments in, and sets `status = 'uploaded', uploaded_at = now()`, all in the caller's one transaction; `heartbeat()` upserts `producer_heartbeats`. `transcriber/transcriber/cli.py` holds the loop: `process_claim()` fetches audio, marks `audio_fetched`, transcribes, marks `low_speech` or `transcribed`, and uploads, marking `failed` on a fetch error, a model error, or an upload error (four sites, each `tdb.mark_status(conn, claim.transcript_id, "failed" or "low_speech", ...)`); `run_loop()` claims with `claim_meeting()` when `cfg.meeting_id` is set and `claim_next()` otherwise, counts `uploaded`, `failed`, and `low_speech`, and heartbeats each outcome; `main()` returns 1 when `--meeting-id` was given and `not any(counts.values())`, else 0. `Claim` is a frozen dataclass of six fields (`transcript_id`, `meeting_id`, `external_id`, `title`, `meeting_date`, `status`); `transcriber/tests/test_cli_loop.py` builds it positionally and stands in for every `db` function with `FakeDB` through `_wire()`, whose name list is `claim_next`, `claim_meeting`, `mark_status`, `heartbeat`, `roster_for_meeting`, `upload`. `transcriber/transcriber/__init__.py` is one line, `__version__ = "0.2.0"`, which the heartbeat carries.

The Railway side's public readers are in `src/docket/services/transcripts.py`. `_PUBLIC_PREDICATE` is `({a}.status = ANY(%s) OR ({a}.status IN ('failed', 'needs_review') AND {a}.uploaded_at IS NOT NULL))`, formatted by `public_predicate(alias)` and used by `get_public_transcript()` (line 68, the transcript page and the meeting page's `has_transcript` link in `src/docket/web/public.py` lines 290 and 330), `excerpt_for_item()` (line 171, the item page's "From the video" block), and `search_transcripts()` (line 259, the search page's transcript hits); each passes `list(PUBLIC_STATUSES)` as the `%s` parameter, where `PUBLIC_STATUSES = ("uploaded", "speakers_resolved", "events_extracted", "compared")`. The comment above the predicate (lines 21 to 23) says a worker-stage failure after upload must not take a readable transcript off the site and that "Producer failures never set uploaded_at, so they stay hidden", which the re-run path made false.

Every other reader of `transcripts.status`, found by `grep -rn "FROM transcripts\|JOIN transcripts\|UPDATE transcripts" src scripts` on 2026-10-16, and what the re-run's transitions mean to it after this plan: `list_transcript_debt()` in the same service file (line 303) lists `failed`, `needs_review`, and some `low_speech` rows on the data-debt page; a row in flight is at a producer status and not listed, and a restored row reads as it did before, so nothing changes. `held_transcripts()` and `retry_transcript()` in `src/docket/services/discrepancies.py` (lines 141 and 152) take `needs_review` and `failed` rows with `uploaded_at` set; after M2 the producer never writes `failed` on such a row, so the held tab lists worker failures only, as it was written to. The worker's `CLAIM_SQL` in `src/docket/ai/transcripts/pipeline.py` (line 30) takes `uploaded`, `speakers_resolved`, and `events_extracted` rows with `stage_attempts < 3` and `last_attempted_at IS NULL OR last_attempted_at < now() - interval '24 hours'`, and stamps `last_attempted_at = now()` on its claim; a row in flight is at a producer status and cannot be claimed, and after M2 a fresh upload arrives with `last_attempted_at` NULL (today the producer's `transcribed` write stamped it), so the worker takes it at the next tick instead of the following day's; `advance()`, `mark_low_speech()`, `mark_needs_review()`, `mark_rate_limited()`, `mark_transient()`, `reset_for_versions()`, and `sweep_minutes_changes()` in that file touch only worker statuses and are unchanged. `src/docket/web/admin.py` line 539 counts rows by status for the admin AI panel and shows whatever is there. `producer_stalled()` in `src/docket/ai/transcripts/alerts.py` looks only for meetings with no row. `scripts/transcript_recompare.py` line 37 moves a `compared` row to `events_extracted`. ## Plan of Work

M1, the Railway side. In `src/docket/services/transcripts.py` delete the line `PUBLIC_STATUSES = (...)`, replace the three-line comment and `_PUBLIC_PREDICATE` with:

    # A transcript is public once uploaded, whatever the producer or a worker
    # stage does to its status afterwards (a re-claim for re-transcription, a
    # worker-stage failure, a hold), except low_speech, which both writers use
    # to mean there is no usable transcript. uploaded_at is written only by the
    # producer's upload() in the transaction that publishes the segments, and a
    # producer failure on a never-uploaded row leaves it NULL.
    _PUBLIC_PREDICATE = "({a}.uploaded_at IS NOT NULL AND {a}.status <> 'low_speech')"
