# Split transcript segments at speaker changes, drop hallucinated and prompt-leaked segments, and let the producer re-transcribe one meeting

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This document must be maintained in accordance with `plans/PLANS.md`.

## Purpose / Big Picture

docket.pub transcribes Birmingham City Council video on a desktop machine (the Lenovo Legion, a Windows 11 PC with an NVIDIA GPU) and uploads the transcript, one row per segment of speech, to the Railway Postgres database. The code that does this is the producer under `transcriber/`. The public page `/al/birmingham/meetings/<id>/transcript/` renders those rows as turns, one per speaker, and the Railway worker later resolves which council member each diarization cluster is (a cluster is the label such as `SPEAKER_07` that the diarization model gives to one voice it heard). The operator reviewed all 48 transcripts uploaded so far (9,233 segments, archived on the Legion at `C:\docket-archive\transcripts`) and found three defects, all in the producer.

First, the producer's segments are the roughly 28-second chunks that faster-whisper's batched pipeline emits (median 27.5 seconds, 85 percent over 20 seconds in the operator's review; 26.8 seconds and 80 percent in the in-repo fixture), and `assign_clusters()` in `transcriber/transcriber/engine.py` gives a whole chunk to the one cluster that overlaps it most. A speaker change inside a chunk is lost: 315 cluster changes in the review fall mid-sentence, and in 40 of the 48 transcripts the whole roll call (the clerk reading nine names, nine people answering "here") sits inside one segment under one cluster. The worker's `find_roll_call_pairs()` in `src/docket/ai/transcripts/speakers.py` looks for a short name segment followed by a short response from another cluster, so on these transcripts it finds nothing; on the fixture for meeting 2543 it finds 0 pairs today. The producer already captures word-level timestamps (it writes them to `words.json` beside the upload), so the fix is to assign a cluster to every word from those timestamps and cut each chunk wherever the cluster changes. Second, 180 short, low-confidence segments in the review are hallucinations Whisper produces over applause or silence, such as "Thank you for joining us." and "Thank you. Thank you.", with `avg_logprob` around -1.1 (the fixture has seven such rows between -1.05 and -1.37). Third, the initial prompt built by `transcriber/transcriber/prompt.py`, which ends in a comma list `Terms: ALEA, CJI, APC, Alabama Power, BJCC, ...`, is transcribed back as if spoken in meetings 1, 4, 8, and 2543 (fixture row seq 38 reads `ALEA, CJI, APC, Alabama Power, BJCC, Woodlawn, Ensley, Avondale, Pratt City, Norwood, Smithfield,`).

After this plan, a transcript produced by the new code has one segment per speaker turn rather than per 28-second chunk, carries no hallucinated filler and no copy of the prompt, is marked `transcripts.version = 2` so it can be told apart from the 48 version-1 uploads, and the producer can be pointed at one meeting with `--meeting-id 2543` to replace an earlier upload in a way the worker's comparison stage treats as changed input. How to see it working: `venv/bin/python -m pytest transcriber/tests -q -p no:cacheprovider` from the repository root prints `31 passed, 10 skipped` today and, after the four milestones, `47 passed, 12 skipped`, with every new test built on a synthetic fixture inside the test and failing on today's code; `./tools/verify` runs that suite as its fifth check and prints `verify: transcriber ... ok`. The operator then re-runs meeting 2543 on the Legion (that run is outside this plan's sessions) and sees shorter turns on the public transcript page, no row containing `ALEA, CJI, APC`, no `Thank you for joining us` rows, and `version = 2` on the `transcripts` row.

## Context and Orientation

## Idempotence and Recovery

Every test and grep above can be rerun freely. `tools/test-db --drop` removes the throwaway database; a session killed mid-verify leaves `docket_test_<hash>` behind, and the next `tools/test-db` rebuilds it. The producer changes are pure functions plus one new claim path; nothing in this plan touches the Railway database or the Legion archive, and the operator's re-run overwrites only the meeting 2543 folder on the Legion and that meeting's rows, which the worker rebuilds from the upload. If `claim_meeting` is run twice, the second run re-claims the same row again (status `claimed`, marker unchanged), which is harmless. If a milestone session cannot finish, split its Progress line in place (completed: X; remaining: Y) and log the split; do not rewrite a line's text.
