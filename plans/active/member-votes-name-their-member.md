# Member votes name their member: resolve minutes votes to council members daily, and never store an unreadable OCR vote as clean evidence

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This document must be maintained in accordance with `plans/PLANS.md`.

## Purpose / Big Picture

docket.pub publishes every Birmingham City Council vote with each member's position, read from the city's own minutes PDF. Each position is a row of the `member_votes` table carrying the name the minutes print (`Woods`, `O’Quinn`) and, when it is known, the `council_member_id` of the person it refers to. The member pages at `/al/birmingham/members/<id>/` (attendance, alignment, voting history, the dated dissent view) and any future reader that counts roll calls per member read only rows with that id. On production on 2026-10-20, 2032 of the 2680 minutes member votes of the last twelve months (76 percent) carried no id, because `src/docket/services/ingest.py` inserts every minutes member vote with `council_member_id` NULL and the only resolver ever written is the one-shot `scripts/backfill_member_vote_ids.py`, never scheduled and last changed 2026-05-01, whose roster-derived variants use a straight apostrophe and so cannot match the curly one the minutes print in `O’Quinn`. After this plan a reader notices three things. A member vote ingested from the minutes carries its member id the moment it is inserted, a daily worker task sweeps whatever is still unresolved, and the one-time run of that task on production, by the operator, takes the twelve-month unresolved count from 2032 to a small residue of names that are not on the roster. A video OCR vote whose header could not be read is stored flagged for review, with its own reason, instead of as a clean vote with the result `unknown` and no nay count (five such rows exist on production). And `./tools/verify` proves the matching against the real roster the migrations seed, so the rule cannot rot silently at the next council transition.

The city page plan on branch `plan/birmingham-city-briefing` (pull request #128, not on `main` when this plan was authored) holds the deploy of `main` until this plan merges, because its daily `briefing_facts` task would otherwise compute the council cards over about a quarter of the real roll calls; its record of that is the 2026-10-20 Decision Log entry of `plans/completed/birmingham-city-briefing.md` and the row `D64` of `docs/DEBT.md`, both on that branch. This plan does not touch `src/docket/services/briefing.py` or anything else that lives only there.

## Decision Log

- Decision: the rule lives in one new module, `src/docket/services/member_votes.py`, with a pure resolver (`RosterIndex.resolve`) that both the insert path and the daily sweep call; the sweep groups unresolved rows by municipality, stored name, and meeting date, resolves each group in Python, and writes one `UPDATE ... WHERE mv.member_name = %s AND m.meeting_date = ANY(%s)` per (municipality, stored name, member id) bucket.
  Rationale: `docs/PRINCIPLES.md` One owner per fact: a SQL re-statement of the variant rule beside the Python one would be a second owner. The script wrote one UPDATE per name using the first row's meeting date for the term check, which maps every `Smitherman` row, before and after 2025-10-28, to one member; grouping by date applies the term window to every row. The statement count is bounded by distinct name-member pairs (about thirty for Birmingham), each scoped by a `WHERE` on name and dates and touching each row once, which is the shape decision `0026` and the Production is not a sandbox principle ask for; the row count written is the same under any grouping, and the one-time production run writes roughly the 2032 rows of the window plus the older residue, well under the 57,000-row sweep `0026` records.
  Date/Author: 2026-10-20, plan author (Claude, under `cycle-plan`).
- Decision: a name that matches more than one member in the same municipality and term window is left unresolved and logged, and a vote on a meeting whose `meeting_date` is NULL is left unresolved; a member whose `term_start` or `term_end` is NULL is unbounded on that side.
  Rationale: Source or silence: the script's tie-break could not break a tie (Surprises), so its behaviour was "the first roster row wins", a guess. No Birmingham roster row shares a surname today, so this changes nothing on production and prevents a wrong id at the next transition. A NULL meeting date gives no evidence of which term applies. NULL term dates are how migration 005 seeded the three cities that have no votes, and the script treated them as unbounded; keeping that avoids a silent change for a roster the resolver never meets.
  Date/Author: 2026-10-20, plan author.
- Decision: the script's `is_garbage_name` DELETE is not carried over. The sweep never deletes a row; an unresolved name is logged by name and count (the thirty most common, then "and N more").
  Rationale: a `member_votes` row inserted from the minutes is evidence of what the parser read; a parser-noise name (`Georgia`, `Friday`) is a parser bug to fix in `src/docket/analysis/minutes_parser.py`, and deleting the row hides the bug and the count. Keep the sources apart and Evidence or silence both point the same way. The log line is what tells the operator the noise exists.
  Date/Author: 2026-10-20, plan author.
- Decision: the resolver reads the roster through `load_roster_index(municipality_id)` in its own short read (`db_cursor()`), and `_ingest_votes` calls it once per meeting before its insert transaction, not inside it.
  Rationale: a dozen roster rows per city; a separate read keeps the function signature free of a cursor and lets the unit tests build an index from rows without a database. Services own transactions either way.
  Date/Author: 2026-10-20, plan author.
- Decision: `src/docket/analysis/ocr/rosters.py` is not edited, so `D33` does not fire; the service builds the initial-dot-surname variant itself, which overlaps `_to_initial_lastname` there.
  Rationale: the OCR layout's member names drive spatial matching on video frames, and a change to how they are built is a pipeline change decision `0028` says is compared on real rows before it ships; this plan has no OCR frames to compare on. Importing a private name from the analysis layer into a service would be allowed by the layer map but couples two rules that may need to diverge (the service also drops generational suffixes such as `II`, which the OCR key for Homewood's `Paul S. Simmons II` does not). The overlap is two lines and is named in the spec.
  Date/Author: 2026-10-20, plan author.

## Context and Orientation

docket.pub is a Python 3.10 application: a Flask site, an APScheduler worker on Railway, and PostgreSQL. `AGENTS.md` is the map; `docs/PRINCIPLES.md` holds six rules that outrank convenience, and the two that bind this plan most are Source or silence (a value the source does not supply is shown as missing, never filled with a guess) and Evidence or silence (a change is reported as working only after the command that proves it ran). ## Idempotence and Recovery

Every step can be rerun. The sweep touches only rows whose `council_member_id` is NULL and writes each at most once per run; a second run finds nothing. The insert-path change is covered by the existing `votes_scanned` guard, so a meeting is never ingested twice. The operator's UPDATE has `needs_review = FALSE` in its `WHERE`, so a rerun prints `UPDATE 0`. No migration is added and no row is deleted by any step. `tools/test-db --drop` removes the throwaway database after any by-hand tier run; `./tools/verify` drops its own on every exit path. If a milestone session runs out of room, it splits its Progress line in place (completed: X; remaining: Y), logs the split, commits, and stops. If `./tools/verify` fails at the start of a session on something this plan did not touch, that is a Surprises entry and the session does not absorb the fix.
