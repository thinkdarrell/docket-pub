# Video votes land on the item voted: a vote read off the video at the next item's cue point is attached to the item whose roll call it closes

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

This document must be maintained in accordance with `plans/PLANS.md`.

## Purpose / Big Picture

docket.pub reads Birmingham City Council roll calls off the meeting video (the "video OCR" votes, `votes.source = 'video_ocr'`, each stamped with the second of the Granicus clip at which the vote display showed its result) and files each one under an agenda item, so that an item's page can say "9–0, passed" with a "Watch this vote" link. Today the filing rule is: the item whose cue point (the second at which the clerk marked that item as beginning in the Granicus player, `agenda_items.video_timestamp_seconds`) is the latest one at or before the vote's second. That rule is wrong at the one place a clerk is busiest. A roll call closes, the result appears on screen, and in the same second the clerk advances the player's index to the next item, so the vote's second lands on, or a few seconds after, the *next* item's cue point and the vote is filed under the item that has not started yet, with confidence 1.0 and nothing to flag it. GitHub issue #142 is the reproduction: on meeting 3184 (2026-10-27), vote 12396 at second 2256 is item 3's roll call (the transcript has item 3 opened at 2145, its roll call 2191 to 2255, and the clerk saying "Item three passes. Next item." and then "Should be at 64"), but item 64's cue point is also 2256, so the vote sits on item 64 at `/al/birmingham/items/63046/` and item 3 at `/al/birmingham/items/62985/` shows no vote. Counted on production on 2026-11-07, 78 of the 237 video votes with an active attachment sit within 10 seconds of their item's cue point, 2 more within 11 to 30 seconds, and the remaining 157 at 31 seconds or more; the gap distribution has two humps with almost nothing between them, and every one of the 78 has an earlier cued item in its meeting. If the reading above holds for all of them, about a third of the video votes on the site are filed one item late.

After this plan, three things are true. First, the rule is settled by evidence before it is changed: the operator runs a read-only script this plan adds against production, which prints, for each near-cue vote, its two candidate items and the transcript's words around the vote, reads which item's roll call the words name, and records the verdicts and the threshold they support in this plan's Decision Log. Second, `match_votes_by_timestamp` in `src/docket/analysis/vote_matcher.py` attaches a video vote that lands within that threshold of an item's cue point to the latest item with an earlier cue second (vote 12396 goes to item 3, 111 seconds after its cue, confidence 1.0), proved by tests that fail before the change; the daily `vote_matching` worker task applies the rule to new meetings on its own. Third, the attachments already stored on production are moved by one bounded operator step with a dry run and a count before and after: a new script lists every move (vote, meeting, old item and its cue, new item and its cue, gap), the write deactivates each moved link and inserts the new one in one statement per direction, never deletes or revives a row by accident, and a second dry run prints zero moves. On the site, `/al/birmingham/items/62985/` then shows the 9–0 vote 12396 as item 3's prevailing vote and `/al/birmingham/items/63046/` shows only vote 12397 with nothing in its history. In the repository, `./tools/verify` prints `verify: all 6 checks passed` at the end of every milestone.

The timed video links (the "Watch this vote on YouTube" link itself, `src/docket/services/video_links.py`, decisions `0078`, `0079`, and `0082`) are not at fault and are not touched: the link opens the attached item's moment correctly; only the attachment is wrong.

## Decision Log

- Decision: the rule is settled by an operator's reading of transcripts before the code milestone, and the plan is cut so that M1 equips that reading (a read-only listing with the transcript words), the operator's verdicts and threshold go in this log, and M2 reads them from here.
  Rationale: the goal asks for a transcript-checked sample before the rule changes, and no factory session can read production (the scoping session's one read-only query was refused by the permission system; every production read in earlier plans was done in the operator's session). A plan that guessed the threshold would ship a rule chosen by the author's reasoning about clerks, which is exactly what the issue says cannot be ruled out without reading. The alternative, settling it at authoring from the counts alone (78 near zero, 2 between, 157 far), was rejected because the counts show the humps and not which item the near-zero votes belong to. The listing is built as code rather than pasted as SQL because the re-match dry run of M3 needs the same listing (vote, old item and cue, candidate item and cue, gap), so M1's module is not throwaway.
  Date/Author: 2026-11-07, plan author (Claude).

- Decision: the default rule, adopted unless the sample contradicts it, is: when the gap from a video vote to the latest cue point at or before it is at most `NEAR_CUE_S` seconds and the meeting has an item with a strictly earlier cue second, the vote is attached to the latest such item and its confidence is scored from the gap to that item; `NEAR_CUE_S` is 10 unless the sample moves it; the step back is taken once, not repeated.
  Rationale: the issue's distribution puts 78 votes within 10 seconds and 2 in the next 20, then 157 at 31 or more; 10 is the gap between the humps and the figure the issue counted with. One step back, not a walk to the first item whose gap exceeds the threshold, because a consent agenda is read with cue points one or two seconds apart (the real cue points of meeting 2543 in `tests/fixtures/transcript_2543/agenda_items.json` run 3043, 3046, 3047, 3049, 3050, 3053, 3053, …), and a repeated walk would carry a consent vote back through the whole run to the block's first item while the gap-based confidence lost its meaning; one step lands it on a consent item of the same block, which links to the same moment under the consent rule of `docs/specs/video-links.md`. Items that share one cue second are skipped together because "strictly earlier cue second" says so; the clerk clicked them as one.

## Context and Orientation

### The terms this plan uses

A video OCR vote is a `votes` row with `source = 'video_ocr'`, produced by `src/docket/analysis/ocr/pipeline.py` from the meeting video, carrying `video_timestamp` (REAL, seconds on the Granicus clip's clock at which the vote display showed its result; the three votes of meeting 3184 are at 2138.5, 2256, and 2325.5), `result`, `yeas`, `nays`, and `needs_review`. A cue point is `agenda_items.video_timestamp_seconds` (REAL), the second at which the clerk marked an item as beginning in the Granicus player; an item ingested before the recording existed has none until `_backfill_video_timestamps` in `src/docket/services/ingest.py` fills it, and a filled value is never replaced (`docs/specs/video-links.md`, "Where a cue point and a chapter id come from"). An attachment, or link, is a `vote_agenda_items` row (migration 009): `vote_id`, `agenda_item_id`, `association_type` (`explicit` for every timestamp link), `match_method` (`timestamp` for every link the rule below writes), `match_confidence`, `provisional`, `is_manual`, `is_active`, `created_at`, `updated_at`, with `UNIQUE (vote_id, agenda_item_id)`. Every reader of links filters on `is_active` (`get_vote_for_item`, `list_votes` through `Vote.active_links`, the member page's two history queries, all in `src/docket/services/query.py`); the item page at `/al/<slug>/items/<id>/` shows `get_vote_for_item`'s prevailing entry (manual first, then newest meeting, then `explicit` before consent types, then highest vote id) and the rest as history. The meeting page (`src/docket/web/templates/meeting_detail.html`) prints under each vote "Re: #<item number>. <title>" with a chip holding the method and the confidence, or "No agenda item linked." A transcript is a `transcripts` row, one per meeting (`meeting_id UNIQUE`), whose words are `transcript_segments` rows (`transcript_id`, `seq`, `start_s`, `end_s`, `text`, `is_silence`), uploaded by the desktop transcriber; on a Granicus meeting their seconds are on the same clock as the votes and the cue points.

### The rule today

`match_votes_by_timestamp(meeting_id)` in `src/docket/analysis/vote_matcher.py` (lines 135 to 187) reads the meeting's cued items ordered by `video_timestamp_seconds` (ties in no stated order), reads every `video_ocr` vote of the meeting with a timestamp and no active link, and for each vote takes `idx = bisect_right(item_timestamps, vt) - 1`, the last item whose cue is at or before the vote; a vote before the first cue is skipped. The gap `vt - item_timestamps[idx]` goes to `compute_confidence` (lines 74 to 89): 1.0 under 120 seconds, 0.8 under 600, 0.5 under 1800, 0.3 beyond, halved when the vote has `needs_review`. The link is written by `_upsert_link` (lines 92 to 132) as `explicit`, `timestamp`, `provisional = FALSE`; its `ON CONFLICT` updates method, confidence, excerpt, and `updated_at` only where `is_manual = FALSE`, and never touches `is_active` (the existing test `test_match_votes_for_meeting_ignores_inactive_ghost_links` pins that a ghost row stays inactive). The function opens its own transaction with `db()`, as the rest of the module does, contrary to the `ARCHITECTURE.md` invariant that services own transactions; no row of `docs/DEBT.md` names it, and M4 adds one. ### States that would make the new attachment false, and what the plan does about each

A vote on the first cued item of a meeting, at or just after that item's cue: there is no earlier item, so the vote stays where it is; M2 pins it. Two or more items sharing one cue second: they are one click, and the step back goes to the latest item whose cue is strictly earlier than theirs; M2 pins it. A consent vote inside the consent run: one step back lands on another consent item of the same run, which links to the same moment under the consent rule, and the item page of a consent item already shows the minutes' consent vote first when the minutes exist (`get_vote_for_item` sorts `explicit` before consent types within a meeting date, so the video vote is the prevailing one on the item it is attached to; this is how things stand today and the plan does not change it). A manual link (`is_manual`): never visited by the matcher (it has an active link) and excluded from the re-match by its WHERE clause; M3 pins it. ## Idempotence and Recovery

Nothing in M1 writes. The matcher change in M2 affects only votes with no active link, so running `vote_matching` twice does what it did before: nothing the second time. The re-match is repeatable: a moved link no longer matches (its old row is inactive, its new row's item is the rule's answer), so a second run reports zero moves; a run killed between its two statements is rolled back by `db()`, which commits only when the block exits without an exception. The write is reversible from the database alone, because nothing is deleted: one `UPDATE vote_agenda_items SET is_active = TRUE, updated_at = NOW() WHERE (vote_id, agenda_item_id) IN ((<vote>, <old item>), ...)` and one `UPDATE vote_agenda_items SET is_active = FALSE, updated_at = NOW() WHERE (vote_id, agenda_item_id) IN ((<vote>, <new item>), ...)`, with the pairs taken from the dry-run lines (each prints the vote id and both item ids), restore the old state under the one-statement rule of decision `0026`; the dry run's output is kept for that reason. The manual pin of after-merge step 3 is undone by the same UPDATE with `is_manual = FALSE` over the same vote ids, which the Decision Log entry names. `tools/test-db` rebuilds the throwaway database at any time and `tools/test-db --drop` removes it. A milestone that will not fit is split in place in Progress (completed: X; remaining: Y) with a Decision Log entry, and the session stops.

### The count query (the issue's table, run before and after the re-match)

    SELECT CASE WHEN v.video_timestamp - a.video_timestamp_seconds <= 10 THEN '0-10 s'
                WHEN v.video_timestamp - a.video_timestamp_seconds <= 30 THEN '11-30 s'
                ELSE '31 s or more' END AS gap,
           count(*) AS votes, count(DISTINCT v.meeting_id) AS meetings
      FROM vote_agenda_items vai
      JOIN votes v ON v.id = vai.vote_id
      JOIN agenda_items a ON a.id = vai.agenda_item_id
      JOIN meetings m ON m.id = v.meeting_id
      JOIN municipalities mu ON mu.id = m.municipality_id
     WHERE mu.slug = 'birmingham'
       AND vai.is_active AND vai.match_method = 'timestamp'
       AND v.source = 'video_ocr' AND v.video_timestamp IS NOT NULL
       AND a.video_timestamp_seconds IS NOT NULL
     GROUP BY 1 ORDER BY 1;
