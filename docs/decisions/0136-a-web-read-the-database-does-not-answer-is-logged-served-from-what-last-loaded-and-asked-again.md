# 0136 — A web read the database does not answer is logged, served from what last loaded, and asked again

## Decision

A read in the web process that fails is logged with the error it raised, the reader is served from what that read last loaded, the read is asked again 30 seconds after the failed attempt ended, and a thread that has something to serve never waits for another thread's attempt. It holds today in two places: the source-link allowlist (`get_allowlist` in `src/docket/web/source_security.py`) and the blog's posts (`init_blog_state` and the blueprint's `before_request` function in `src/docket/web/blog.py`).

## Rationale

Decision `0135` gave the web process two database limits it did not have: a connection attempt gives up after 10 seconds and a statement is ended after 30. A database that is merely slow then reached two handlers that caught every exception, answered without what the database would have given, and logged nothing. The allowlist served only its six fixed domains for ten minutes, so a page answered 200 with a city's source link withheld, which is what "Source or silence" in `docs/PRINCIPLES.md` exists to prevent; the blog stayed empty for the life of the process, and only another deploy mended it. Rows `D207` and `D208` of `docs/DEBT.md` recorded the two, and plan `source-links-and-blog-survive-a-slow-db` paid both and deleted them.

The alternatives, and what each would have cost. Keeping the fixed set but for a shorter time still withholds a link the database had just allowed, only more briefly, and more often under a database that fails now and then; the kept list is exactly a list the database gave, never a wider one, and its one cost is that a city set inactive while the database is unreachable stays allowed until a read succeeds, with a log line at every failed try. Failing the start when the blog's posts do not load takes the whole site down for a blog the site does not link to: the start line runs the migrations against the same database seconds earlier, so what reaches `create_app` is a database that answered then and is slow a moment later, 54 test files call `create_app()`, and tooling calls it without a database. Telling a database error from any other (retry the driver's errors, log anything else once and stop) would have the web layer import the driver, which nothing under `src/docket/web/` does, and a wrong classification leaves the blog empty for good; the uniform rule cannot loop, because its bound is on time (two attempts a minute at most, and only while blog addresses are asked for), so a malformed post costs one log line and one re-read of the files at that rate until a deploy fixes the file. Answering 503 from the blog while its posts are not loaded is the more exact answer and changes seven routes and their feeds for a state that lasts until the next blog request 30 seconds on; the routes answer as for an empty blog (the hub 200 with no post, a post's address 404), every blog response carries `X-Robots-Tag: noindex`, and the empty hub is this choice, not an oversight. It is worth weighing again when posts are linked from elsewhere on the site or indexed, because a 404 for a post that exists can then be cached by whatever followed the link. Discarding the kept list when the operator presses `POST /admin/source-security/refresh` would turn that button, pressed while the database is failing, into the failure itself; `invalidate_cache()` forces the next call to ask and keeps the last list and the record that the last attempt failed, a city is removed by setting it inactive and the next read that succeeds, and `forget_allowlist()`, which discards everything, is for tests. Recovery lines at info level would not be printed: nothing configures logging in the web process, so a module logger's record reaches `railway logs` only through Python's last-resort handler, which prints warning and above, and the operator's step in row `D206` reads for those lines.

Thirty seconds is the statement limit. An attempt can hold one thread for at most 30 seconds, so with the interval counted from the end of the attempt (on `time.monotonic()`, which cannot be stepped) at most one of the four threads is asking and for at most half the time. A thread with something to serve does not wait because under a 30-second retry the wait would be nearly constant while the database ends every statement at its limit, and every page with a source link would wait for an answer it does not need; only a caller with nothing at all (the first request of a process, for the allowlist) waits, since the alternative is the fixed set in a process whose database is well. The blog's hook skips the asset route, which reads no post, and checks under its lock that the pending object is still the one in `app.config`, so two threads never load twice.

What binds a later change. The lines are an interface: each is one line (the error's text has its white space collapsed, the driver's ending in a line break), begins `source allowlist:` or `blog:`, names the error's type and text, and carries the phrases `docs/specs/operations.md` and row `D206` tell the operator to search for. A failure is at warning when something loaded is still being served and at error when nothing has loaded in the process; the blog prints a traceback at the start and afterwards only when the error's type is new. A third place that needs the rule gets it in this shape; two hand-written copies did not justify a shared helper, and a third might.

What was observed when this was written: 24 tests added by the plan (fourteen for the allowlist, ten for the blog), two of them against a local socket that accepts a connection and never answers, 21 of them failing against the old code's behaviour and three passing there because the old code already did what they pin (no line and nothing kept when nothing has failed); 23 single removals from the allowlist's rules and 30 from the blog's each failed a test. Production had not been read under either: the start line of `0135` was merged and not deployed (`D206`). On 2026-11-23 production's allowlist added nothing to the six fixed domains (one stored `base_url`, Birmingham's, already under `granicus.com`), so the links `D207` described as withheld were on that day none; the rule is for the first city whose files are on its own host.
