# 0049 — A transcript is public once uploaded unless it is `low_speech`, a re-run that ends without an upload restores the pre-claim row, and `last_attempted_at` is the worker's column alone

## Decision

A `transcripts` row is public once `uploaded_at` is set unless its status is `low_speech`: `public_predicate()` in `src/docket/services/transcripts.py` is `uploaded_at IS NOT NULL AND status <> 'low_speech'`, there is no list of public statuses, and a row passing back through the producer statuses for a `--meeting-id` re-run keeps its old segments on the site until `upload()` replaces them. `claim_meeting()` in `transcriber/transcriber/db.py` reads a previously uploaded row whole before its claim (only a row resting at `uploaded` or a worker status, never at a producer status, which is a crashed re-run) and carries it on the `Claim` as `prior`; a re-run of such a row that ends `failed` or `low_speech` hands `prior` to `restore_row()`, which writes every column except `id` and `meeting_id` back, so the row after the failure is the row before the claim and the failure is recorded only in the producer's log line, its exit code, and `producer_heartbeats.last_status`. `last_attempted_at` is written by the worker's `CLAIM_SQL` in `src/docket/ai/transcripts/pipeline.py` alone; the producer's `mark_status()` never stamps it, so the 30-minute busy guard reads only the worker's claim.

## Rationale

This record extends decision `0048`, which chose to re-claim the existing row in place and accepted, as its cost, that the row passes back through the producer statuses with `uploaded_at` set and the old segments still in the table. The closing review of `plans/completed/transcriber-clean-speaker-segments.md` found what that cost did: the page was a 404 for the hour a re-run takes, a `low_speech` re-run hid it for good, a `failed` re-run surfaced the old transcript under `failed` in the admin held tab, and the producer's own status stamp tripped a busy guard whose docstring blamed the worker. The obvious alternatives each cost more than the rule above. A new status such as `retranscribing` needs a migration altering the CHECK in `src/docket/migrations/035_transcripts.py` and a change at every reader of `status`, where keying the predicate on `uploaded_at` needs neither: `uploaded_at` is written only by `upload()` in the transaction that publishes the segments and is never cleared, so it is exactly "segments have been published", and `low_speech` is excluded because both writers of it mean "there is no usable transcript here". Carrying the claim outside the row, so the row never left its status, would need a second place the worker's `CLAIM_SQL` and `advance()` check before writing, which they do not. A snapshot column for the pre-claim state cannot be added by the `transcriber` role, which `scripts/sql/create_transcriber_role.sql` grants only `SELECT, INSERT, UPDATE, DELETE` on the producer tables; that same grant is why `restore_row()` may write every column, and writing every column is what makes "the same row" literal rather than approximate, since the pre-claim status may be any worker status and the claim resets five other columns. The snapshot lives in memory because nothing else can write the row while the producer holds it at a producer status; a producer that dies mid-run loses it, and the next run of that meeting ends as a first run would, which the spec names with its recovery.

The trap this record guards against is the agent who "tidies" `_end_without_upload()` in `transcriber/transcriber/cli.py` into `mark_status(..., 'failed')` because a failure should look like a failure in the row: that reintroduces a producer-failed row with `uploaded_at` set, which the held tab lists and a retry from there restarts the worker on the old events with the `transcript_changed` marker discarded. The second trap is making `mark_status()` stamp `last_attempted_at` again for symmetry with the worker's claim: the column is the busy guard's only input, and a producer stamp refuses the operator's second `--meeting-id` for 30 minutes after a failed one and delays a fresh upload past the worker's 24-hour backoff. The third is restoring `PUBLIC_STATUSES` beside the predicate because a list reads more clearly than a rule: a status list is a second owner of the fact, and a status it omits goes dark.
