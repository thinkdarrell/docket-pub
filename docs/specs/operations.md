# Operations

How docket.pub is run today: environments, tests, deploys, Railway, the domain, and the transcriber. Present tense. The cron schedule itself is the code in `src/docket/worker/scheduler.py`; this file does not restate it.

## Local environment

Python 3.10 is required; `requirements.lock` is compiled for it and the Dockerfile and Railway use it.

    python3.10 -m venv venv
    venv/bin/pip install -e ".[dev]"       # reads requirements.lock via pyproject, deterministic
    cp .env.example .env

Each git worktree needs its own `venv/`. The editable install pins the `docket` package to the checkout it was installed from, so a worktree that borrows the main checkout's venv tests the main checkout's code. `node` must be on `PATH` (Homebrew's `/opt/homebrew/bin/node`; v26.8.2 is the release the scripts have been checked with), because `tools/check-workflows`, the fourth check in `./tools/verify`, parses the saved workflows with `node --check` and fails without it. The git hooks live in `tools/hooks/` and are activated once per clone, in that clone's main checkout, with the command below; linked worktrees share the repository's configuration, so the one setting covers every factory worktree, while a separate clone (a second checkout elsewhere on the same machine) needs the command again.

    git config core.hooksPath tools/hooks

`requirements.txt` holds the top-level dependencies with loose ranges; `requirements.lock` is the pinned tree. The Dockerfile and `pyproject.toml` both read the lock, so local, CI, and Railway resolve the same versions. When a dependency changes, edit `requirements.txt` and regenerate the lock in the same commit:

    uv pip compile requirements.txt --python-version 3.10 -o requirements.lock

Migrations and the dev server:

    venv/bin/python -m docket.migrations.runner            # apply pending
    venv/bin/python -m docket.migrations.runner --status
    venv/bin/python -m docket.migrations.runner --down <version>   # rolls back migration number <version>

`--down` takes a migration number, not a count: `--down 35` rolls back 035, and `--down 1` runs 001's down SQL, which drops the whole schema.
    venv/bin/flask --app docket.web:create_app run

The application is the factory `create_app` in `src/docket/web/__init__.py`, the same object the `Procfile` and the `Dockerfile` hand to gunicorn; nothing in the checkout names it for a bare `venv/bin/flask run` (no `wsgi.py`, `app.py`, or `.flaskenv`, and no `FLASK_APP` in a worktree's `.env`), which exits 2 with `Could not locate a Flask application`.

Docker is an alternative for the database and app together: `docker-compose up -d`.

Local PostgreSQL without Docker is version 16 from Homebrew:

    /opt/homebrew/opt/postgresql@16/bin/pg_ctl -D /opt/homebrew/var/postgresql@16 start
    /opt/homebrew/opt/postgresql@16/bin/pg_ctl -D /opt/homebrew/var/postgresql@16 stop
    /opt/homebrew/opt/postgresql@16/bin/createuser -s docket      # first time only
    /opt/homebrew/opt/postgresql@16/bin/createdb -O docket docket_db

Then `DATABASE_URL=postgresql://docket@localhost:5432/docket_db` in `.env`.

## Tests

One command runs everything that does not call Anthropic:

    ./tools/verify

Its wall time and budget are stated once, in `AGENTS.md` Commands; it exits zero only when every check passed. It first runs `tools/test-db`, which builds a disposable database on the server that `DATABASE_URL` names (the `.env` value when the variable is unset in the shell; the role in that URL must be allowed to create databases, which `createuser -s` above grants, or the build fails with `permission denied to create database` and no tier runs, `D57`) by applying every migration, in one to three seconds (the verify summaries recorded in the two factory plans show `test-db ... ok` at 0 s, 1 s, and once 3 s). The database is named `docket_test_<hash>`, where `<hash>` is the first eight hex characters of the SHA-1 of the checkout's absolute path, so two checkouts never share one and the name is the same from any directory inside a checkout; `tools/test-db --drop` removes it. With `DATABASE_URL` exported at that database, verify runs the fast tiers (`tests/unit`, `tests/web`, `tests/services`), the integration tier (`tests/integration`), the milestone judge's fixture self-test (`tools/fixtures/judge/run`), the saved-workflow shape check (`tools/check-workflows`), as the fifth check, the producer suite (`transcriber/tests`, run with the same `venv/bin/python`), and, as the sixth, the active-plan check (`tools/check-plans`), prints one `verify: <name> ... ok (Ns)` or `verify: <name> ... FAILED (Ns)` line per check with each failing check's own output above the summary, ends with `verify: all M checks passed in Ss.` or `verify: N of M checks failed in Ss.` followed by one indented command per failing check that re-runs it alone on a disposable database, and drops the database on every exit path. Every check runs even when an earlier one fails; the one exception is a failed database build, after which no tier runs and verify exits 1, because without the exported URL the unit tier would delete rows from `docket_db` (`D37`).

A stale developer `docket_db` is no longer what the tests run against: `./tools/verify` neither reads nor changes it, so drift in it cannot make the suite red, and the suite's own leftovers (the rows and the materialised-view drift that `D37` and `D38` describe) vanish with the disposable database. Expected on a fresh database: the fast tiers report `5 skipped`, four in `tests/web/test_p5_translation.py`, whose data-dependent cases skip when no meetings, tagged items, search hits, or coverage rows exist, and one in `tests/web/test_city_overview_render.py`, which skips when there is no Birmingham meeting to render; that is expected, not a failure (`D41`). The producer suite's database tests in `transcriber/tests/test_db.py`, which skip when `DATABASE_URL` is unset, run rather than skip under verify because the throwaway database's URL is exported to that check too. Tests that insert rows own their cleanup, the migration tests apply and roll back real migrations against the disposable database, and the integration tier keeps pytest's default file order (`D38` says why).

To run one tier by hand on a disposable database: `DATABASE_URL=$(tools/test-db) venv/bin/python -m pytest tests/integration -q -p no:cacheprovider`, then `tools/test-db --drop`. `tools/test-db` writes its progress and the migration runner's output to stderr and the URL alone to stdout, which is what makes the `$(...)` form work. It refuses, with exit 2 and one line on stderr before it touches the server, a `DATABASE_URL` that names no database after the host and any argument other than `--drop`; if the migration run fails it drops the database it was building.

Live tests make real Anthropic calls and need a real `ANTHROPIC_API_KEY`: `venv/bin/python -m pytest -m live`. Bare `pytest` no longer collects them, because `pyproject.toml` sets `addopts = "-m 'not live'"` and an explicit `-m live` replaces that expression. `tests/conftest.py` refuses, with exit status 2 and before any test is collected, a `DATABASE_URL` (from the shell, or from `.env` when the shell has none) whose database is not named `docket_test_*`, because the unit tier deletes rows from whatever it names (`D37`); the guard is `tests/conftest.py`'s, so it covers the tiers under `tests/` and not `transcriber/tests`, which has no conftest; the exemption is the exact marker expression `live`, so a single live test is run as `venv/bin/python -m pytest -m live tests/live/<file>` and any other expression (`-m 'live or slow'`, `-m 'not live'`, none) against such a database is refused.

The milestone judge, `tools/judge-milestone`, decides from a plan file and the git history alone whether a session advanced exactly one milestone; `AGENTS.md` Commands says how it is run, its contract is `docs/capabilities/judge-milestone.md`, and its twelve-case self-test is verify's third check. Verify's fourth check, `tools/check-workflows`, reads every `.claude/workflows/*.js`, requires its first statement to be a literal `export const meta = { ... }` whose `name` is the file's basename and whose `description` is non-empty, wraps the rest in an async function and runs `node --check` on it, and refuses a body that calls `Date.now(`, `Math.random(`, `new Date()`, or `import(`, which the Workflow runtime forbids; it prints `workflows: N of N ok` and exits 0, or names the file and the reason and exits 1, and an empty `.claude/workflows/` is a failure. Verify's sixth check, `tools/check-plans`, runs the judge's `snapshot` mode over every `plans/active/*.md` and prints `plans: <path> ... ok (Progress, Surprises & Discoveries, Decision Log, Outcomes & Retrospective)` per plan and `plans: N of N ok` (exit 0), or `plans: <path> ... FAILED` with the judge's `judge: defect ...` line and the remediation from `docs/capabilities/evidence-check.md` indented beneath it and `plans: K of N failed` (exit 1); an empty `plans/active/` prints `plans: no active plans` and passes. The same script with `--staged` is the body of `tools/hooks/pre-commit`, which judges the index version of every staged active plan, so a commit that stages a plan missing a living section or ticking a Progress entry without a date is refused where `core.hooksPath` is set (Local environment above).

Continuous integration. `.github/workflows/verify.yml` runs `./tools/verify`, and nothing else, on every push to any branch and on every pull request to `main`, in a job named `verify` on `ubuntu-latest` with Python 3.10 (`actions/setup-python`, pip cache keyed on `requirements.lock`), a `postgres:16` service container as user `docket` with `DATABASE_URL=postgresql://docket:docket_dev@localhost:5432/docket_db` (so `tools/test-db` builds its `docket_test_<hash>` database on that server), the runner image's own Node and `psql`, and one `apt-get install tesseract-ocr` step, because the OCR tests under `tests/unit/ocr/` call the real `tesseract` and the first run without it failed sixteen of them. A pull-request branch therefore runs twice per push, once for each event. The first green run (2026-10-18, run 39082127893) took 4 minutes 14 seconds end to end (containers 17 s, `tesseract-ocr` 20 s, venv and install 29 s) with `./tools/verify` itself at `verify: all 6 checks passed in 176s.` (fast tiers 77 s, integration 93 s), inside the job's `timeout-minutes: 20`.

## Running the factory

The factory is the pair of saved Claude Code workflows under `.claude/workflows/`, `cycle-plan.js` and `cycle-run.js`. A saved workflow is a JavaScript file the Workflow tool runs in an isolated runtime with no shell, filesystem, or clock; the script only coordinates agents, and each agent it starts is an ordinary subagent with `AGENTS.md` injected and the Bash, Read, Edit, Write, Grep, and Glob tools. Each file's `meta.name` is its command, so `/cycle-plan` and `/cycle-run` work in any session whose working directory is inside the repository; a script added or edited during a session is picked up after `/reload-skills`, or can be run by path with `Workflow({scriptPath: '.claude/workflows/<name>.js', args: ...})`. Runs are watched in `/workflows`. Every run writes its script and its agents' transcripts under the session's directory in `~/.claude-personal/projects/`, and the tool's launch message prints the run id, that directory, and the script path. One run happens at a time: every worktree shares the one local PostgreSQL server, `tools/test-db` keeps their test databases apart by name, but two runs would also compete for the operator's attention and the same `origin`, and concurrent runs are not supported.

`/cycle-plan <goal>` is run from any checkout of the repository with the goal stated in a sentence or two. A guard agent checks the checkout, the `origin` remote, the `gh` login, and that `tools/judge-milestone` and `tools/verify` exist; a scope agent reads `AGENTS.md`, `GOALS.md`, `docs/DEBT.md`, `docs/capabilities/index.md`, the open GitHub issues, and the code the goal touches, and writes a brief (outcome, slug, files, debt paid and tripped, specs altered, out of scope, questions). When the brief holds questions only the operator can answer, the run stops with `status: 'questions'` and lists them; the operator reruns `/cycle-plan` with the answers appended to the goal. Otherwise a setup agent runs `git worktree add -b plan/<slug> .claude/worktrees/<slug> origin/main` from the main checkout and builds the worktree's `venv/` (`python3.10 -m venv venv && venv/bin/pip install -e ".[dev]"`); a plan-author agent follows `skills/plan-author/SKILL.md` in the new worktree and commits `plans/active/<slug>.md` alone as `plan: <slug>, authored`; and a check agent confirms `tools/judge-milestone snapshot` exits 0 on the new plan with open entries only, the tree is clean, and exactly one commit sits over `origin/main`. The result is `status: 'planned'` with the branch, worktree, plan path, milestone count, first milestone and its acceptance, what was left out, and the venv build time. Before running the plan the operator reads it, records any change as a dated Decision Log entry naming themself as author, commits it in the worktree, and starts a new Claude Code session in that worktree. A refusal at any stage returns `status: 'refused'` with the reason and, once the worktree exists, a `cleanup` line (`git worktree remove --force .claude/worktrees/<slug>; git branch -D plan/<slug>` from the main checkout), because the setup stage is not idempotent: a second run with the same slug fails at `git worktree add`.

`/cycle-run plans/active/<slug>.md` is run from a session started in `.claude/worktrees/<slug>` on branch `plan/<slug>`, optionally with a limit on the number of milestones for this run (`/cycle-run plans/active/<slug>.md 1`; without a limit the run executes every open milestone, up to a hard cap of twenty, and then closes the plan). Preflight is one agent that checks the worktree, branch, plan file, clean tree, `origin`, remote reachability, `gh` login, that `venv/bin/python` imports `docket` from this worktree, `./tools/verify`, and `tools/judge-milestone snapshot`; any miss halts before a milestone starts. Each milestone then runs as three agents: a snapshot agent records `HEAD` and the plan's Progress with `tools/judge-milestone snapshot`; a milestone session, a fresh agent given `skills/plan-execute/SKILL.md`, executes the first open milestone and commits; a judge agent runs `tools/judge-milestone judge` against the snapshot and then `./tools/verify`. The run logs `cycle-run: advanced "<entry>" in <seconds>s, verify <last line>` and moves to the next open entry. When no open entry remains the closing sequence runs: a diffstat agent fetches `origin` and measures the range from `origin/main`; three reviewers (correctness, scope against the plan, data honesty) read the diff in parallel, each told to refute its own findings; a record agent deduplicates them and commits one `Decision: review record.` entry into the plan's Decision Log as `plan: <slug>, review record`; a retro agent follows `skills/retro/SKILL.md` (which moves the plan to `plans/completed/`); a doc-garden agent follows `skills/doc-garden/SKILL.md`; a final verify agent runs `./tools/verify` and requires a clean tree; and a publish agent pushes `plan/<slug>` and opens the pull request with `gh pr create --base main`, whose body is the plan's Outcomes & Retrospective followed by the review record. The result is `status: 'complete'` with the milestones landed, the review counts, and `pr_url`; a run stopped by its limit returns `status: 'advanced'`.

A halt is a returned result, not an error, and prints four lines: `cycle-run: halt <plan>`, `cycle-run: milestone <entry or none>`, `cycle-run: <the rule that failed>` (the judge's own lines, `./tools/verify failed at <sha>: <last line>`, `review found <n> severe finding(s); see the review record in <plan>`, `agent <label> returned no result`, and the like), and `cycle-run: fix the cause in the worktree, commit, and re-run /cycle-run with the same arguments`. Resuming is exactly that: fix the cause, commit in the worktree, and rerun the same command. Preflight and the snapshot run again, milestones already ticked are skipped, and the cost is one `./tools/verify`. A halt inside the closing sequence is different. Before the retro stage (diffstat, review panel, review record) a rerun with the same arguments works but is not idempotent: it appends a second review record to the plan. From the retro stage on, the plan has been moved to `plans/completed/<slug>.md`, and a rerun with the same arguments is refused by preflight (the plan file is gone from `plans/active/`) while the new path is refused as not a plan under `plans/active/`; the operator finishes the remaining stages by hand in the worktree: run `skills/doc-garden/SKILL.md` if it had not run, `./tools/verify`, `git push -u origin plan/<slug>`, and `gh pr create --base main` with the plan's Outcomes & Retrospective as the body. The publish stage, when it does run, recognises an existing pull request for the branch and completes with its URL. That is `D43` in `docs/DEBT.md`, accepted at L0 because the operator reads the plan before merging.

## Deploying

A human deploys, from a clean `main` after the pull request has merged:

    git checkout main && git pull
    scripts/deploy.sh --service docket-web
    scripts/deploy.sh --service worker

The wrapper writes the current HEAD SHA to `./COMMIT_SHA` before invoking `railway up --detach` and deletes the file when it exits; the Dockerfile moves it to `/app/COMMIT_SHA`. `COMMIT_SHA` is deliberately not gitignored, and `.gitignore` carries the reason beside its rules: the Railway CLI honours `.gitignore` for uploads, so an ignored file would never reach the build. The wrapper refuses, with exit 3 and before it writes `COMMIT_SHA` or invokes `railway`, a working tree with uncommitted changes (`git status --porcelain` not empty) and then a branch other than `main`; a wrapper that dies mid-deploy leaves `COMMIT_SHA` behind, `git status` shows it, and that leftover blocks the next deploy until it is removed. To see which commit a service is running:

    railway ssh --service docket-web "cat /app/COMMIT_SHA"
    railway ssh --service worker     "cat /app/COMMIT_SHA"

A bare `railway up` still works but records the literal string `unknown`, because the Railway CLI strips `.git` from uploads. Deploying only from a clean `main` is a constraint in `GOALS.md`, and decision `0022` records why. GitHub refuses a push to `main` and a merge whose commit's `verify` status check (the `verify` job of `.github/workflows/verify.yml`) is not green, administrators included; the pull-request route itself remains a working rule, not a setting, and decision `0052` records why and holds the `gh api` command that recreates the protection. Because the workflow runs on both the push and the pull-request event, a pull request shows two check runs named `verify`; with both green, pull request #124's merge state read `CLEAN` under the protection (`gh pr view 124 --json mergeStateStatus`, 2026-10-18), and whether one green run alone satisfies the required context has not been observed. Never use `railway redeploy`; it restarts the old build without new code.

The `web:` process runs the migrations and then gunicorn serving `docket.web:create_app()` (see `Procfile`). The worker is a separate Railway service with a custom start command; decision `0023` says why, and `scripts/deploy.sh --service worker` redeploys it.

## Railway specifics

`railway run <cmd>` executes locally with Railway's variables injected, and the injected `DATABASE_URL` points at `postgres.railway.internal`, which resolves only inside Railway's network. `railway ssh --service <name> "<cmd>"` executes inside the container. For anything that touches the production database from a laptop, use `DATABASE_PUBLIC_URL`:

    DATABASE_URL=$(railway variables --service docket-web --kv | grep DATABASE_PUBLIC_URL | cut -d= -f2-) \
    ANTHROPIC_API_KEY=$(railway variables --service docket-web --kv | grep '^ANTHROPIC_API_KEY=' | cut -d= -f2-) \
    venv/bin/python -m docket.ai.cli --status

Manual worker tasks run inside the container: `railway ssh --service worker` then `python -m docket.worker.scheduler --run-once <task>`. A long `railway ssh "<cmd>"` can return before the remote command finishes; poll the relevant table rather than chaining commands.

Dumps and restores from a laptop use the postgresql@18 binaries (`/opt/homebrew/opt/postgresql@18/bin/pg_dump`, `psql`); the version 16 binaries refuse with a server version mismatch. The version gap is a constraint in `GOALS.md`.

The worker's memory ceiling and the ban on a second heavy Python process are constraints in `GOALS.md`; `railway ssh --run-once <heavy task>` starts exactly such a process and has caused out-of-memory kills. If headroom shrinks, the options are a larger tier, `LIMIT 1` per OCR tick, or a separate OCR service.

Feature flags in production: `IMPACT_FIRST_ENABLED=true` on `worker` (the v3 pipeline writes) and `SMART_BREVITY_UI=true` on `docket-web` (citizen rendering of v3 cards) are on. `MINUTES_VS_VIDEO_UI` on `docket-web` stays unset until the transcript ship gate on `/admin/ai` reads "met" (decision `0032`). `TRANSCRIPT_PER_TICK` (default 5) bounds the worker's transcript stage advances per tick. Flags are read in `src/docket/config.py` and `src/docket/web/__init__.py`; Railway holds the values.

Backfills run from a laptop against `DATABASE_PUBLIC_URL`. The archived 2023 Birmingham meetings come from `scripts/backfill_archived_meetings.py --manifest scripts/manifests/birmingham_2023_archived.json`, which caches agenda PDFs on disk and paces Wayback requests; no minutes exist online for those meetings, so they carry agendas and video only.

Birmingham's YouTube recordings come from the worker task `youtube_ingest` (daily, after `ingest_all`; `src/docket/worker/scheduler.py`, `docs/runbooks/cron-worker.md`), which needs `YOUTUBE_API_KEY` on the `worker` service: a Google Cloud API key restricted to "YouTube Data API v3", whose free quota of 10,000 units a day the whole channel uses about 100 of (decision `0070`). Without the key the task logs `YOUTUBE_API_KEY is not set; nothing read` and succeeds. The whole channel is matched once with `scripts/backfill_youtube_meetings.py --city birmingham`, from a laptop with `DATABASE_URL` set to `DATABASE_PUBLIC_URL` and the key in `YOUTUBE_API_KEY`, after an `ingest_all` has stored the Granicus clips' durations (`SELECT count(*) FROM meetings WHERE municipality_id = <bhm> AND external_id ~ '^[0-9]+$' AND duration_s IS NULL` near 0; a nonzero `no_duration` count in the script's output says it has not). The order is a `--dry-run` first, its output kept and its ambiguous days and create count read, then the write, then a second `--dry-run`, which prints zero creates and zero attaches; the script prints one line per decision in date order, the ambiguous days, and the counts, and exits 1 without a key. The matching rules are in `docs/specs/meeting-types.md`, "The council's YouTube channel". Undoing the YouTube source is `DELETE FROM meetings WHERE municipality_id = <bhm> AND external_id LIKE 'yt-%' AND created_at >= '<the first YouTube write, from the task's or the script's log>'` plus `DELETE FROM meeting_videos WHERE provider = 'youtube'`, under the rule below. The bound is the rows' creation time, not their meeting date, because the backfill reads the channel back to 2008 and creates rows for any year; the 2023 Boutwell `yt-` rows were created long before and are untouched. Rows the `video` rung named fall back to the next rung at the following `ingest_all`. The transcriber downloads a `yt-` meeting's audio with yt-dlp, which its image carries from `transcriber/requirements.txt` (rebuild with `docker compose build` after that file changes); `transcriber/README.md`, "YouTube recordings", names the optional cookie file `TRANSCRIBER_YTDLP_COOKIES`.

Bulk changes on production are one targeted SQL statement. The volume size is a constraint in `GOALS.md`; the incident behind the rule is decision `0026`.

The Railway project also holds a second Postgres service, `Postgres-pKpA`; `D32` in `docs/DEBT.md` is the open question of what it is for.

## Domain and headers

The apex `docket.pub` is on Railway with a Let's Encrypt certificate it provisions itself. DNS at Namecheap: `CNAME @` to `zu815cqb.up.railway.app` plus a `TXT _railway-verify` record. `www.docket.pub` is a Namecheap URL redirect over HTTP only; moving it to Railway is `D10`.

`src/docket/web/__init__.py` sends `Strict-Transport-Security: max-age=31536000` in an `after_request` hook when `FLASK_ENV` is not `development`, without `includeSubDomains`; decision `0025` says why and `D10` tracks the change.

## Transcriber

The desktop producer on the Legion is the Transcriber component in `ARCHITECTURE.md`; it connects as the `transcriber` database role, created once by `scripts/sql/create_transcriber_role.sql` (decision `0030`). Rotate it with `ALTER ROLE transcriber PASSWORD '...'` and update the transcriber's .env file on the Legion (not in this repository). Uploads are public on arrival. Operating notes, expected oddities (stray Monday Granicus clips, over-split speakers), and the bring-up log are in `transcriber/README.md`; the runbook is `docs/runbooks/transcripts.md`.
