# Transcript comparison

How docket.pub compares what was said at a Birmingham City Council meeting against the official minutes, and what happens to a finding a human has already reviewed when the comparison runs again. Present tense. This file covers only the comparison stage, `run_compare_stage` in `src/docket/ai/transcripts/compare.py`; the rest of the transcript pipeline (upload, speaker resolution, event extraction, retries, the review queue, the ship gate, alerts) is in `docs/runbooks/transcripts.md`.

## What a comparison pass writes

A pass starts from two event timelines, one extracted from the transcript and one from the minutes PDF. `align()` in `src/docket/ai/transcripts/aligner.py` pairs them deterministically into candidates: a transcript event with no minutes counterpart (`omission`), a minutes event with no transcript counterpart (`addition`), a pair whose details differ (`wording`, `speaker`, or `vote_outcome`), or a pair out of order (`sequence`). Every candidate except the `vote_outcome` ones goes to a language model called the judge, which keeps or dismisses each one; the full texts go to a second model call called the hunter, which reports what the aligner missed. `build_rows()` in `compare.py` turns candidates, judge verdicts, and hunter findings into rows of `minutes_discrepancies`, with every quoted excerpt verified by the guard against the text the model saw (a quote the guard cannot find keeps the row with `citation_match = 'missing'`), and `write_rows()` hands them to `reconcile()`.

A row's `review_state` is one of `proposed`, `approved`, `rejected`, `dismissed_by_model`, or `stale`. `src/docket/services/discrepancies.py` owns the human transitions: `approve()` moves a `proposed` row to `approved` and refuses a row whose `citation_match` is `missing`. The public meeting page shows `approved` rows only (`list_public_for_meeting()` and its two siblings in the same file).

## Which categories a model may assign

The six categories are `vote_outcome`, `omission`, `addition`, `wording`, `sequence`, and `speaker` (a CHECK constraint in `src/docket/migrations/035_transcripts.py`). `vote_outcome` is written only by the deterministic tally check, the first loop of `build_rows()`: a candidate the aligner marked `vote_outcome` becomes a row with `severity = 'material'` and `origin = 'aligner'`, with no model involved. A judge verdict or a hunter finding that names `vote_outcome` is written as `wording`, and the remap is logged at INFO as `remapped a model-assigned vote_outcome to wording`; `model_category()` in `compare.py` does this on both paths before the row's category is used for anything else, so a remapped hunter row folds into an aligner `wording` row on the same anchor like any other wording row (issue #114). The fold-in in `build_rows()` tests the hunter's original category as well as the remapped one against the aligner rows already built, so a hunter restating the deterministic tally mismatch on the same transcript event folds into the `vote_outcome` row instead of becoming a second `wording` row. The judge and hunter prompts in `src/docket/ai/transcripts/prompts.py` and the `Literal` types in `schemas.py` still list `vote_outcome`; removing it is debt `D50` in `docs/DEBT.md`, paid with the next `COMPARE_PROMPT_VERSION` bump.

## How a vote result is read

`canonical_result()` in `aligner.py` reads a result string from either side and returns no outcome, `fail`, or `pass`, in that order of checks. A result that names a continuation (`carried over`, `carried forward`, `tabled`, `withdrawn`, `postponed`, `continued`, `deferred`, `no action`) is no outcome. Otherwise the negation clause (`not adopted`, `not approved`, `not carried`, `not granted`) and the fail stems (`fail`, `deny`/`denies`/`denied`/`denial`, `defeat`, `reject`, `lost`) read `fail`; fail is checked before pass, so "motion to deny approved", "motion to deny carried", and "the council approves the denial" all read `fail`, and the Birmingham denial "the motion to approve NOT adopted and the above resolution adopted" reads `fail`. Otherwise the pass words (`adopted`, `approve`/`approved`, `pass`/`passes`/`passed`, `carried`, `granted`, `prevail`, `sustained`) read `pass`. Anything else is no outcome. `_results_differ()` reports a vote-outcome mismatch only when both sides name an outcome and the outcomes differ, so a side that reads no outcome skips the comparison rather than guessing (issue #116). "approved" against "adopted" is the same outcome and is at most a `wording` finding.

## Re-comparison

The comparison runs again on three paths: the weekly `sweep_minutes_changes()` in `src/docket/ai/transcripts/pipeline.py`, when a compared meeting's minutes PDF hash changed; `reset_for_versions()` in the same file, after a `COMPARE_PROMPT_VERSION` bump; and `run_for_meeting()`, which `scripts/transcript_recompare.py` drives by hand. What a pass does to rows a human already reviewed is the policy in `reconcile()`, keyed on one column the claim carries, `transcripts.compare_skipped_reason`: `'minutes_changed'` is written only by the weekly sweep and the script with `--minutes-changed`; `'transcript_changed'` is written by the `EVENTS_PROMPT_VERSION` branch of `reset_for_versions()` and the script with `--transcript-changed`, because re-extracting the transcript side deletes the events every row is anchored to. `run_compare_stage` derives `minutes_changed` and `transcript_changed` from that column and, when the first is set, also re-extracts the minutes side before comparing. `advance()` in `pipeline.py` leaves the column alone when a stage before compare reports no reason, so the marker survives the events stage's own status write; two writers still discard it, `retry_transcript()` in `src/docket/services/discrepancies.py` (NULL) and an events stage whose minutes check fails (its own reason), so a transcript retried from the held tab after either runs an unchanged-input pass (`D52` in `docs/DEBT.md`).

Every pass first deletes the meeting's `dismissed_by_model` rows; the model's old dismissals are replaced wholesale. A pass with `minutes_changed` or `transcript_changed` set then sets every `approved` and `proposed` row to `stale`, recording the old state in `previous_review_state`; any other pass stales only `proposed` rows, because on unchanged input the only thing that can make a finding vanish is the model deciding differently, and a human's approval outranks that. Each new row is then matched against the meeting's `stale`, `rejected`, and `approved` rows by `match_stale()`: same category and the same `transcript_event_id`, or for rows with no transcript event, same category and agenda item with a minutes-excerpt similarity of at least 0.8. A matched row is updated in place and keeps its id. On a `transcript_changed` pass the re-extraction has already set every row's `transcript_event_id` to NULL (the foreign key is `ON DELETE SET NULL`), and `match_stale()` matches an anchored new row only on a shared anchor, so a returning anchored finding is inserted as a new `proposed` row beside the stale approval and only unanchored `addition` rows re-match by excerpt (`D51` in `docs/DEBT.md`). A matched `stale` row becomes `proposed` again with its reviewer columns cleared, and the admin queue badges it "re-review" from `previous_review_state`. A matched `rejected` row stays `rejected`, keeping `reviewed_at`, `reviewed_by`, and `review_note` while its title, description, severity, excerpts, confidence, and `prompt_version` are refreshed. A matched `approved` row is not rewritten at all: the public page says a person reviewed it, so it keeps every column the person approved, including its text, excerpts, severity, and the `prompt_version` that produced them, and the match only stops the same finding from being inserted again beside it (`reconcile()` counts it as `kept` in its return value and its log line). An unmatched new row is inserted as `proposed`; an unmatched `stale` row stays `stale`, visible under the queue's stale tab (issue #112).

`reset_for_versions()` re-queues a compared meeting for the compare stage only when it has a `proposed` or `dismissed_by_model` row below the current `COMPARE_PROMPT_VERSION`. Approved rows survive an unchanged-minutes pass at the `prompt_version` that produced their text, and rejected and stale rows are never re-stamped, so counting any of them would re-compare the meeting on every tick after a bump. The consequence: a meeting whose only live rows are approved is not re-compared by a prompt bump; the operator re-runs it with `venv/bin/python scripts/transcript_recompare.py --meeting-id N --now`, which without a flag writes `compare_skipped_reason` as NULL and keeps every approved row untouched, with `--minutes-changed` runs a minutes-changed pass, and with `--transcript-changed` runs a transcript-changed pass; the two flags are mutually exclusive.
