# Transcript comparison

How docket.pub compares what was said at a Birmingham City Council meeting against the official minutes, and what happens to a finding a human has already reviewed when the comparison runs again. Present tense. This file covers only the comparison stage, `run_compare_stage` in `src/docket/ai/transcripts/compare.py`; the rest of the transcript pipeline (upload, speaker resolution, event extraction, retries, the review queue, the ship gate, alerts) is in `docs/runbooks/transcripts.md`.

## What a comparison pass writes

A pass starts from two event timelines, one extracted from the transcript and one from the minutes PDF. `align()` in `src/docket/ai/transcripts/aligner.py` pairs them deterministically into candidates: a transcript event with no minutes counterpart (`omission`), a minutes event with no transcript counterpart (`addition`), a pair whose details differ (`wording`, `speaker`, or `vote_outcome`), or a pair out of order (`sequence`). Every candidate except the `vote_outcome` ones goes to a language model called the judge, which keeps or dismisses each one; the full texts go to a second model call called the hunter, which reports what the aligner missed. `build_rows()` in `compare.py` turns candidates, judge verdicts, and hunter findings into rows of `minutes_discrepancies`, with every quoted excerpt verified by the guard against the text the model saw (a quote the guard cannot find keeps the row with `citation_match = 'missing'`), and `write_rows()` hands them to `reconcile()`.

A row's `review_state` is one of `proposed`, `approved`, `rejected`, `dismissed_by_model`, or `stale`. `src/docket/services/discrepancies.py` owns the human transitions: `approve()` moves a `proposed` row to `approved` and refuses a row whose `citation_match` is `missing`. The public meeting page shows `approved` rows only (`list_public_for_meeting()` and its two siblings in the same file).

## Which categories a model may assign

The six categories are `vote_outcome`, `omission`, `addition`, `wording`, `sequence`, and `speaker` (a CHECK constraint in `src/docket/migrations/035_transcripts.py`). `vote_outcome` is written only by the deterministic tally check, the first loop of `build_rows()`: a candidate the aligner marked `vote_outcome` becomes a row with `severity = 'material'` and `origin = 'aligner'`, with no model involved. A judge verdict or a hunter finding that names `vote_outcome` is written as `wording`, and the remap is logged at INFO as `remapped a model-assigned vote_outcome to wording`; `model_category()` in `compare.py` does this on both paths before the row's category is used for anything else, so a remapped hunter row folds into an aligner `wording` row on the same anchor like any other wording row (issue #114). The judge and hunter prompts in `src/docket/ai/transcripts/prompts.py` and the `Literal` types in `schemas.py` still list `vote_outcome`; removing it is debt `D50` in `docs/DEBT.md`, paid with the next `COMPARE_PROMPT_VERSION` bump.

## How a vote result is read

`canonical_result()` in `aligner.py` reads a result string from either side and returns no outcome, `fail`, or `pass`, in that order of checks. A result that names a continuation (`carried over`, `carried forward`, `tabled`, `withdrawn`, `postponed`, `continued`, `deferred`, `no action`) is no outcome. Otherwise the negation clause (`not adopted`, `not approved`, `not carried`, `not granted`) and the fail stems (`fail`, `deny`/`denies`/`denied`/`denial`, `defeat`, `reject`, `lost`) read `fail`; fail is checked before pass, so "motion to deny approved", "motion to deny carried", and "the council approves the denial" all read `fail`, and the Birmingham denial "the motion to approve NOT adopted and the above resolution adopted" reads `fail`. Otherwise the pass words (`adopted`, `approve`/`approved`, `pass`/`passes`/`passed`, `carried`, `granted`, `prevail`, `sustained`) read `pass`. Anything else is no outcome. `_results_differ()` reports a vote-outcome mismatch only when both sides name an outcome and the outcomes differ, so a side that reads no outcome skips the comparison rather than guessing (issue #116). "approved" against "adopted" is the same outcome and is at most a `wording` finding.

## Re-comparison

The comparison runs again on three paths: the weekly `sweep_minutes_changes()` in `src/docket/ai/transcripts/pipeline.py`, when a compared meeting's minutes PDF hash changed; `reset_for_versions()` in the same file, after a `COMPARE_PROMPT_VERSION` bump; and `run_for_meeting()`, which `scripts/transcript_recompare.py` drives by hand. What a pass does to rows a human already reviewed is the policy in `reconcile()`, keyed on one fact the claim carries: `transcripts.compare_skipped_reason = 'minutes_changed'`, which only the weekly sweep and the script with `--minutes-changed` write. `run_compare_stage` derives `minutes_changed` from that column and, when it is set, also re-extracts the minutes side before comparing.

Every pass first deletes the meeting's `dismissed_by_model` rows; the model's old dismissals are replaced wholesale. A pass with `minutes_changed` set then sets every `approved` and `proposed` row to `stale`, recording the old state in `previous_review_state`; any other pass stales only `proposed` rows, because on unchanged input the only thing that can make a finding vanish is the model deciding differently, and a human's approval outranks that. Each new row is then matched against the meeting's `stale`, `rejected`, and `approved` rows by `match_stale()`: same category and the same `transcript_event_id`, or for rows with no transcript event, same category and agenda item with a minutes-excerpt similarity of at least 0.8. A matched row is updated in place and keeps its id. A matched `stale` row becomes `proposed` again with its reviewer columns cleared, and the admin queue badges it "re-review" from `previous_review_state`. A matched `rejected` row stays `rejected`, and a matched `approved` row stays `approved`, both keeping `reviewed_at`, `reviewed_by`, and `review_note` while their title, description, severity, confidence, and `prompt_version` are refreshed; when the replacement for an approved row carries `citation_match = 'missing'`, the stored excerpts, page, start time, and `citation_match` are kept as well, so an approved row never carries a quote the guard could not find. An unmatched new row is inserted as `proposed`; an unmatched `stale` row stays `stale`, visible under the queue's stale tab (issue #112).

`reset_for_versions()` re-queues a compared meeting for the compare stage only when it has a `proposed` or `dismissed_by_model` row below the current `COMPARE_PROMPT_VERSION`. Approved rows survive an unchanged-minutes pass at the `prompt_version` that produced their text, and rejected and stale rows are never re-stamped, so counting any of them would re-compare the meeting on every tick after a bump. The consequence: a meeting whose only live rows are approved is not re-compared by a prompt bump; the operator re-runs it with `venv/bin/python scripts/transcript_recompare.py --meeting-id N --now`, which without `--minutes-changed` writes `compare_skipped_reason` as NULL and keeps every approved row, and with the flag runs a minutes-changed pass.
