# Video links

Which links into a meeting's video open at a moment, what that moment is, which site each one opens (YouTube at a second, or the Granicus player at a chapter), what the link says about itself, how the transcriber measures where a YouTube recording sits on its Granicus clip's clock, and where an agenda item's cue point and chapter id come from. Present tense. One module builds every such link, `src/docket/services/video_links.py`; templates print the finished link and build no URL. The meeting page's untimed "Watch video" and "Watch on YouTube" links are in `docs/specs/meeting-types.md` (Provenance), and what attaches a YouTube recording to a meeting is in the same file ("The council's YouTube channel").

## The two clocks

Every time stored for a Granicus meeting (a row whose `meetings.external_id` is all digits, the clip id, and whose `video_url` is the player page `MediaPlayer.php?view_id=2&clip_id=<id>`) is on the Granicus clock, seconds from the start of the clip: an agenda item's cue point (`agenda_items.video_timestamp_seconds`), a vote read off the video (`votes.video_timestamp`), a transcript segment, and a discrepancy's `transcript_start_s`. Nothing is stored converted; a link is built from those seconds each time a page renders.

The Granicus player can jump only to a chapter: `&meta_id=<n>` appended to the player URL, where `<n>` is the id of one of the clerk's cue points. It ignores every other way of naming a time. YouTube opens at any second (`&t=<n>s`), but the council's YouTube recording of a meeting does not start when the Granicus clip does. The offset of a recording is Granicus seconds minus YouTube seconds for the same instant, so a moment at Granicus second g is at YouTube second g minus the offset. A meeting that exists only on YouTube (a `yt-` row, whose own `video_url` is the watch URL) has its times on YouTube's clock already and needs no conversion.

## Which links are timed, and each one's moment

The vote link on an agenda item's page (`/al/<slug>/items/<id>/`, the macro `vote_source_link` in `partials/_vote_result_block.html`). `query.get_vote_for_item` sets `VoteEntry.video_link` on every vote whose `video_timestamp` is not NULL (second 0 counts) and whose meeting has a `video_url`; only a vote read off the video carries a timestamp. The link stands for the item, so a vote on the item's own meeting opens the item's moment under the consent rule below (`video_links.vote_link`). When the item has no second of its own, the link opens at the vote's own second and keeps whatever chapter id the consent rule returned, so for an item with a chapter id and no cue point YouTube opens the vote's second and Granicus the item's chapter. One exception, on YouTube alone (decision `0082`): when the item's moment is the consent block's start and the vote was read more than `CONSENT_GAP_S` after the block's end, the link opens YouTube at the vote's own second if a recording covers it, and is the item's link otherwise. A vote on another meeting (the item taken up again later) opens that meeting's video at the vote's own second with no chapter, because the item's chapter id names a chapter of the item's own clip. A vote without both fields has no video link, and the macro links the minutes or the meeting page instead.

The item link on the transcript page (`/al/<slug>/meetings/<id>/transcript/`, `partials/transcript_body.html`), printed on the first turn of each agenda item. `video_links.item_links(meeting_id)` returns a link for every agenda item of a meeting that has a `video_url`, at the item's moment under the consent rule; an item with no moment gets the plain link to the meeting's video.

The link on a minutes-versus-video row, in the public block (the meeting page, the item page, and `/minutes-vs-video/`, behind the `MINUTES_VS_VIDEO_UI` flag) and in the admin discrepancy queue. `discrepancies._attach_video_links` sets `video_link` on each row that `list_queue`, `list_public_for_meeting`, `list_public_for_item`, and `list_public_recent` return. A row quotes specific words, so on YouTube it opens at the row's own `transcript_start_s`; on Granicus, which cannot seek, it opens the chapter of the row's agenda item under the consent rule, or the plain player for a row with no item. A row with no `transcript_start_s`, or on a meeting with no `video_url`, has no link. Each row carries its own meeting's recordings, so the index is correct across meetings.

The video branch of the source button (`partials/source_anchor_button.html`), for an item whose `source_anchor` is of type `video` with a truthy `timestamp_seconds`. It calls the Jinja global `video_link`, which is `video_links.link_for` itself, with the anchor's second, the item's `external_id` as the chapter id, and the anchor's URL. No page includes this partial and nothing in `src/` or `scripts/` writes `agenda_items.source_anchor`, so the branch is exercised only by `tests/unit/test_source_anchor.py`.

## The consent rule

The consent agenda is the block of routine items the council passes with one vote. The clerk reads them out in one quick run, so their cue points land seconds apart inside that reading and mean nothing singly. `video_links.consent_block` finds the reading among a meeting's consent items (`agenda_items.is_consent`) that have a cue point: it is the largest run of cue points in which neighbours are at most `CONSENT_GAP_S` (120 seconds) apart, it exists only when that run holds at least `CONSENT_MIN_ITEMS` (3) cue points, and of two runs of one size the earlier is the block. The cue points are ordered by second and then by row id. The block's chapter id is the id of the first cue point in the run that is all digits, and the run's first id when none is.

`video_links.item_moment` applies the rule. A consent item whose cue point lies inside the block (both ends included), or that has no cue point, links to the block's start and the block's chapter. Every other item links to its own cue point and its own id: a non-consent item always, and a consent item whose cue point is outside the block (one pulled off consent and discussed separately, whose `is_consent` flag comes from the printed agenda and stays true) or whose meeting has no block. A consent item with no cue point in a meeting with no block has no moment and gets the plain link.

## How a link chooses its site

`video_links.link_for` decides, from the meeting's `video_url`, the second, and the chapter id.

A meeting with no `video_url` has no link. A meeting whose own video is on YouTube links to that video at the floor of the second, or to the plain watch URL when there is no second or the second is negative. Any other address that is not a Granicus player page is returned unchanged with no site named.

For a Granicus player page, the link opens YouTube when the meeting has an attached recording (`meeting_videos`) whose measurement can be trusted for that second: the measurement's `status` is `passed`; its `method_version` is at least `MIN_METHOD_VERSION` in `video_links.py` (a floor, so a later method's measurement is used as it is; it is 2, so a measurement made by method 1, before the ends of the coverage were checked, is not used, and a row passed at version 2 stays in use beside the rows the transcriber writes at version 3); its `granicus_clip_id` equals the meeting's current `external_id` (a recording moved to another meeting row, or a row whose event id became a clip id, is not used on the strength of an old measurement); the second lies inside the measured coverage, start included and end excluded; and the converted second, the floor of the second minus the offset, is not negative. A recording has one measurement row per confirmed stretch ("The measurement table"), and each passing stretch is tried on its own: the primary recording's stretches first, then the other recordings' by recording row id, and within a recording by where each stretch starts on the Granicus clock (by stretch number when two start at the same second). The first whose span holds the second wins and the second is converted with that stretch's own offset, so a recording that matches its clip at two offsets gives YouTube links inside each stretch. A link may therefore land a fraction of a second early and never late by rounding.

Otherwise the link opens the Granicus player: at the chapter (`meta_id`) when the chapter id is all digits, and at the plain player page when it is not or there is none. That is the result for a recording that has not been measured, was `rejected` or `failed`, was measured below the trusted version or against another clip, or has no stretch that covers the second, which includes a second that falls between two stretches of one recording.

A YouTube URL is always built from the video id as `https://www.youtube.com/watch?v=<id>`, with `&t=<n>s` when there is a second, never by appending to a stored URL. `video_links.youtube_id` reads the id from `watch?v=<id>` on `youtube.com`, `www.`, `m.`, and `music.youtube.com` and from `youtu.be/<id>`; a YouTube address with no readable video id is treated as any other host.

## What a link says

Each link names the site it opens, and says "chapter" only when the link carries one. The vote link reads "Watch this vote on YouTube ↗" or "Watch this vote on Granicus ↗". The transcript, minutes-versus-video, and admin links print `VideoLink.phrase`: "video on YouTube ↗", "video chapter on Granicus ↗" when the Granicus link carries a chapter, "video on Granicus ↗" when it opens the plain player, and "video ↗" for any other host. The source button reads "View Source: video on YouTube at <time> →" with YouTube's own time (no " at ..." when the link carries no second), "View Source: video chapter on Granicus →", or "View Source: video on Granicus →"; on Granicus it prints no time, because the player opens the chapter's start and not the anchor's second. For any other host the button keeps its older markup, "View Source: video at <time> →" on the anchor's URL with `t=<N>`.

## The measurement table

`meeting_video_alignments` (migration 042, reshaped by migration 046) holds one row per confirmed stretch of an attached recording, keyed on `(meeting_video_id, stretch)` and deleted with the recording. A stretch is one contiguous run of the recording that matches the clip at one offset; `stretch` counts from 1 in order of where the coverage starts, and a CHECK keeps it at 1 or more. A recording that was `rejected` or `failed` holds one row with `stretch = 1`. Each row carries `granicus_clip_id` (the clip it was measured against), `method_version`, `status`, `reason`, `offset_s` (Granicus seconds minus YouTube seconds), `granicus_start_s` and `granicus_end_s` (that stretch's coverage, on the Granicus clock), `score`, `runner_up`, `windows`, `windows_confirmed`, and `measured_at`. The rows of one recording are written together and share a clip, a version, and a measuring time. Two stretches of one recording may overlap on the Granicus clock (a recording that replays part of the clip), and no constraint forbids it. The audio is not kept anywhere.

`status` is one of three. `passed`: the two recordings were compared and this stretch met the pass mark; a CHECK requires such a row to carry an offset and a non-empty span. `rejected`: they were compared and no stretch met it; `reason` is `score`, `margin`, `windows`, `no_window`, or `edges`, the row carries the whole recording's offset, score, runner-up, and window counts under its best offset and no span, and it is final until the method version rises. `failed`: the audio of one side could not be fetched, converted, read, or measured; `reason` is the error's class name, a colon, and its message, and the offset, span, score, and window counts are NULL. A row that reads `rejected` with reason `operator` and a span is a passed stretch the owner switched off (below), not a verdict of the matcher.

The transcriber is the only writer, through the `transcriber` database role, which may select, insert, update, and delete the table (decisions `0076` and `0105`): a re-measure deletes the recording's rows and inserts the new ones in one transaction, so a stretch the new measurement does not have does not outlive it. The only readers of `status` are `video_links.for_meetings` and the transcriber's candidate query. Which rows are final depends on the status: a `passed` row at `ALIGN_TRUSTED_VERSION` (2) or later is not measured again, and a `rejected` row is final only at the current `ALIGN_METHOD_VERSION` (3). So raising `ALIGN_METHOD_VERSION` has every rejected recording measured again, and the passed ones as well only when `ALIGN_TRUSTED_VERSION` is raised with it; to have one recording measured again, the database owner deletes its rows. Because the site reads `passed` rows alone, the owner can send every link back to Granicus without a deploy by setting the `passed` rows to `rejected` with the reason `operator`. A `rejected` row with that reason is never a candidate for the measuring pass, whatever its version or clip id, and migration 046 keeps it, so the switch holds through transcriber runs and through a deploy. The restore sets such rows back to `passed` and clears the reason, the offsets and spans having stayed in place. Both statements touch every stretch row and are in `docs/runbooks/transcripts.md`, "Measuring YouTube recordings (the backlog)". The candidate query is the one reader of `reason` (decision `0106`).

## The measuring pass

An ordinary transcriber run (`transcriber/transcriber/cli.py` with none of `--meeting-id`, `--dry-run`, `--cache-audio`, `--capture-inputs`, `--replay`) begins with `measure_pass` in `transcriber/transcriber/measure.py`, after the database connection is made and before the speech model is loaded, so it does not use the graphics card. It measures at most `--measure-limit` recordings (environment `TRANSCRIBER_MEASURE_LIMIT`, default 20; 0 turns it off). `--max-hours` and Ctrl-C bound the pass and the transcription loop as one run, and nothing the pass meets keeps the run from transcribing.

A candidate (`alignment_candidates` in `transcriber/transcriber/db.py`) is a YouTube recording attached to a Birmingham meeting that is not hidden, has an all-digit `external_id`, and a `MediaPlayer.php` `video_url`, and that has no measurement, or a `passed` one below the trusted floor (`ALIGN_TRUSTED_VERSION`), or a `rejected` or `failed` one below the current method version (`ALIGN_METHOD_VERSION`), or one against a clip id other than the meeting's, or a `failed` one more than 7 days old. The query reads a recording by its first stretch, so a recording is one candidate however many rows it holds. Recordings without a usable measurement come before retried failures, then the newest meeting first, the primary recording first within a meeting. A `rejected` row at the current version is not a candidate, and neither is a `passed` row at the trusted floor or later, nor a `rejected` row whose reason is `operator` (the owner's off switch) at any version and against any clip id.

The pass walks its candidates meeting by meeting. The Granicus audio is decoded from the archive's `audio.flac` when the meeting has one and downloaded otherwise, with a pause of `MEASURE_PAUSE_S` after each request to Granicus; each recording's audio is downloaded with yt-dlp in its smallest audio format; both are converted to 8 kHz mono WAV in the work folder, compared, and deleted as soon as the recording is measured. The archive is only read. Each recording's rows are saved together and committed on their own.

Any error other than a database error while one recording is fetched, converted, read, or measured saves a `failed` row and the pass goes on; a failure on the Granicus side saves one for each of that meeting's candidates. The pass counts failed fetches in a row, one per meeting for the Granicus side and one per recording for the YouTube side, sets the count back to zero at any `passed` or `rejected` result, and ends at `MEASURE_MAX_CONSECUTIVE_FAILURES` (3). A database error (the table is missing, or the role lacks the grant) or anything else that escapes ends the pass with one warning and the run goes on.

The pass logs, on the logger `transcriber.measure`, one line per confirmed stretch of a recording that passed and one line for a recording that was rejected or failed, each `measure meeting <id> clip <clip id> video <video id>: ` followed by `passed stretch <k>/<n> offset=<s>s covers=<from>-<to>s score=<s> runner_up=<s> windows=<confirmed>/<counted>` (`stretch 1/1` for a recording with one), by `rejected (<reason>) offset=<s>s covers=none score=<s> runner_up=<s> windows=<confirmed>/<counted>`, or by `failed (<error>)`, the lines of a recording being logged after its rows are committed; `measure: 3 fetches failed in a row; stopping`, `measure: stop requested; stopping`, or `measure: max-hours reached; stopping` when it ends early; `measure: skipped (<error>)` when a database error or an unexpected one ended it; and `measure done {'passed': p, 'rejected': r, 'failed': f} remaining=<n>`, all four figures counted in recordings and not in stretches, whenever it reaches its end, early or not, and not after a `skipped`. How the operator reads those lines, and the command that works through the backlog, are in `transcriber/README.md`, "Measuring YouTube recordings".

## The method and the pass mark

`transcriber/transcriber/align.py` owns the method and every one of its constants; this section says what the constants mean, and where this file names a value (under Known limits) that module is where it is set. From 8 kHz audio it computes smoothed log band-energy envelopes, cross-correlates the YouTube recording against the clip, and takes the highest peak as the first offset to try. It checks the recording in windows of `WINDOW_S`, finding each window's own best match against the clip once. A recording that dropped and resumed, or was stitched from two pieces, sits at more than one offset, so the candidate offsets are the whole-recording peak and then the best offset of every window whose best match anywhere reaches `CONFLICT_SCORE`, strongest first, leaving out one within `AGREE_S` of a candidate already taken, at most `MAX_OFFSETS` in all. Under each candidate the windows that lie inside the clip are counted, together with one more window that ends where the overlap of the two recordings ends under that offset, and each is classed in this order: a conflict when its best match anywhere reaches `CONFLICT_SCORE` and lies more than `AGREE_S` from the candidate; agreeing when its best match within `LOCAL_SEARCH_S` of the candidate lies within `AGREE_S` of it; quiet otherwise. A stretch is a run of counted windows with no conflict in it, trimmed to its first and last agreeing window: a conflict window ends a stretch and does not reject the recording, and a quiet window between two agreeing ones stays inside. A run is kept when its agreeing share reaches `PASS_WINDOW_SHARE` and its ends confirm: the span from its first window's start to its last window's end is checked from each end in pieces of `EDGE_S` seconds, each by the test a window gets, and the coverage runs from the first piece that confirms to the last, on the Granicus clock and clipped to the clip. A stretch's score is the whole-recording cross-correlation at its candidate's offset, and the runner-up is the best score more than `RUNNER_EXCLUDE_S` from every candidate that kept a run (from the peak alone when none did). `verdict` is the pass mark, and it is applied to each kept run and not to the recording: the score reaches `PASS_SCORE` (`score` otherwise), it exceeds the runner-up by `PASS_MARGIN` (`margin`), and the agreeing share of the run's windows reaches `PASS_WINDOW_SHARE` (`windows`). Each run that passes is a stretch with its own offset, coverage, score, and window counts; a recording's stretches are in order of coverage start and then offset, and the recording is `passed` when it has at least one. A recording with none is `rejected`. Its reason is the first check failed by the run with the most windows under the whole-recording peak (the earliest on a tie; every counted window with none agreeing when the peak has no run), in the order `no_window` (no window was counted), `score`, `margin`, `windows`, and `edges` when that run fails none and no piece of it confirms; its stored figures are the peak's offset and score, the runner-up, and the windows counted and agreeing under the peak. `verdict` still answers `conflict` to a caller that hands it conflict windows; `measure` hands it none, so no row it stores carries that reason. The pieces do not enter the pass mark. A change to the arithmetic or to a constant raises `ALIGN_METHOD_VERSION`, which is 3 since the stretches; a passed row at version 2 stays trusted (`ALIGN_TRUSTED_VERSION`, `MIN_METHOD_VERSION`). Decision `0078` records the data the pass mark was chosen from, `0081` the pieces, and `0104` the stretches.

## Where a cue point and a chapter id come from

A cue point is a marker the clerk places in a Granicus recording where an agenda item begins. The player page lists them as index points, each with a time and an id, and that id is the chapter id. `GranicusAdapter.fetch_agenda_items` in `src/docket/adapters/granicus.py` reads them: an item first ingested from the player page gets the point's id as `agenda_items.external_id` and its time as `video_timestamp_seconds`.

An item ingested from the agenda PDF before the recording existed has the id `event-<n>-<item number>` and no timestamp. Once the meeting has a clip id, `_backfill_video_timestamps` in `src/docket/services/ingest.py` runs on each ingest of that meeting: when the meeting has a numbered item with no timestamp it fetches the player page once, matches index points to items by the "ITEM N" in each point's title (the first point that names a number speaks for it), and writes every change of the meeting in one statement. A NULL timestamp is filled and a stored one is never replaced. An item's `external_id` becomes the point's chapter id when the stored id is NULL or not all digits, the point's id is all digits, exactly one item of the meeting carries that item number, and no other row of the meeting holds or is being given that id; an id left alone for either of the last two reasons is logged at WARNING. The count the pass returns is added to the "Agenda items: N inserted" figure the ingest logs, so that figure includes rows the pass changed.

A meeting whose numbered items all have timestamps is never fetched by that pass, so items that were cued before the pass wrote chapter ids keep their old ids until the operator runs `scripts/correct_agenda_chapter_ids.py --city <slug>` (`correct_chapter_ids` in the same module). It visits the city's clip meetings that have a numbered, cued item whose id is NULL or not all digits, newest first, at most `--limit` (default 50), runs the same pass on each with the precheck skipped, and prints one line per meeting and a totals line; `--dry-run` computes and prints the same and writes nothing. With the precheck skipped the pass logs at WARNING every other reason a numbered item's id is left alone, one line per meeting and reason: the player page has no index points, none of them names an ITEM number, no point names the item's number, or the item's point has no all-digit id. The ingest run does not log those four. A player-page request is followed by the adapter's delay whether or not it succeeded. The rewrite is repeatable and is not reversible from the database alone, since the old id is not kept. The order the operator runs it in is in `docs/specs/operations.md`. The older `scripts/backfill_agenda_timestamps.py` fills timestamps only and never writes a chapter id.

## Known limits

Each of these is a state the code does not detect or does not handle; the debt rows named are in `docs/DEBT.md`.

A YouTube link may land up to 2 seconds (`AGREE_S`) from its moment, and a recording with a step of up to that size in it, such as a brief stream dropout, stays one stretch with the later part that far off. A larger step splits the recording into two stretches, and the stretch rule has limits of its own. A stretch may be as short as one window. A second part too short to lift a whole-recording peak to `PASS_SCORE` is not a stretch and is left to Granicus (a 155-second second part, on the synthetic cases of `transcriber/tests/test_align.py`). At a cut, up to one window on either side is given up and opens Granicus (`D95`). Two stretches of one recording may overlap on the Granicus clock when the recording replays part of the clip, and the first by start wins. A quiet window inside a stretch stays covered, bounded by the window share as before. At most `MAX_OFFSETS` (4) offsets are tried: a recording that matches at five or more is rejected whole, as `margin`, because the offset nothing tried is counted as the runner-up.

A stretch's coverage runs only from its first agreeing window to its last, and inside those two only from the first 60-second piece that confirms to the last, so a quiet part at either edge of a recording, or on either side of a cut inside it, links to Granicus although the recording holds it (up to four minutes at an end on the labelled recordings), and no window is anchored to the start of the overlap, so the first minutes of a recording that starts before its clip are not covered (`D95`). A recording shorter than one window, five minutes, is rejected as `no_window` (`D97`).

Other audio at the start or the end of a recording (a cut, an edit, a holding slate, silence) is left out of the coverage by the pieces, with two limits that decision `0081` accepts: the piece that holds the boundary can confirm on its matching part, so up to 60 seconds of other audio can stay covered, and a piece of other audio confirms by accident about one time in twenty, which can leave more. A moment in such a stretch opens YouTube at the wrong second. A Granicus clip trimmed in place after it was measured keeps its clip id, so its stored offset is stale and nothing detects it (`D99`). A video removed from YouTube after it was measured still receives links (`D101`).

At a cut inside a recording that does not fall on the 60-second piece grid, the piece that holds the cut can confirm on its matching part, so the earlier stretch's coverage can run up to one piece past the cut and the later stretch's can begin up to one piece before its part does (40 seconds past and 10 seconds before on the synthetic cases of `transcriber/tests/test_align.py` and of plan `youtube-links-cover-matching-stretches`). A moment there opens YouTube at a second that is wrong by the difference of the two offsets (`D152`). The off switch of The measurement table covers the rows stored when it is run and not a recording measured afterwards, which gets `passed` rows and links to YouTube until the statement is run again (`D153`).

A consent item whose vote was read off the video long after the consent block, while the item's cue point is inside the block or missing, has a vote link that opens the later vote on YouTube only: on Granicus, and wherever no measured recording covers the vote's second, it still opens the reading of the consent agenda, because the block's chapter is the only one such an item has (decision `0082`).

A meeting with a numbered item that never gets a cue point has its player page fetched on every ingest run, and any id the rewrite leaves alone there is logged again each time (`D102`). The correction script matches items to index points by agenda number, which is wrong for a meeting first ingested from the player page whose items carry the adapter's fallback ids `<clip>-<position>` (`D105`), and it lists a meeting it cannot fully correct again on every run (`D106`).

The backlog command and a run stopped during the measuring still load the speech model before exiting, and the pass writes no heartbeat (`D103`). The source button treats an anchor at second 0 as untimed, and when a page hands it a `video` it builds the link from that object's `video_url` without the partial's safety check on it (`D104`). A discrepancy row's chapter is taken from whatever agenda item the row names, with no check that the item belongs to the row's meeting.
