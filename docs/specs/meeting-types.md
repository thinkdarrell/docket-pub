# Meeting types

What a meeting's type, sitting, and body name mean, how a row gets them, and what a reader sees. Present tense; the plan that built this is `plans/completed/meeting-types-name-the-body.md`; the `video` rung and the council's YouTube channel came with `plans/completed/youtube-council-channel.md`; the calendar's three readers, the calendar rung's reading of the whole day, the attach by name, and the hiding of clips that are not meetings came with plan `committee-clips-named-or-hidden`.

## The vocabularies

A meeting carries five classification columns on `meetings`: `meeting_type` (the body), `session_kind` (the sitting), `body_name` (the committee or board the row belongs to, when known), `type_source` (which rung of the ladder below named it), and the admin lock pair `type_locked_at` / `type_locked_by`. A sixth, `calendar_event_id`, points at the city-calendar event that named the body when the calendar did.

`meeting_type` is one of `council`, `committee`, `planning`, `board`, `other`. `session_kind` is one of `regular`, `special`, `work_session`, `budget_hearing`. `type_source` is one of `title`, `video`, `calendar`, `schedule_rule`, `admin`. The two vocabularies are the tuples `MEETING_TYPES` and `SESSION_KINDS` in `src/docket/adapters/_helpers.py`, and every other file imports them from there. Migration 038 holds the CHECK constraints on `session_kind` and `type_source` (migration 040 widens the latter with `video`), and migration 039 the CHECK on `meeting_type`, added once production's rows all conformed (the gating query of 2026-11-08 printed no row outside the five); a write with a value outside either vocabulary is refused by the database (decision `0084`). `meeting_type` stays nullable and a NULL passes the CHECK; no writer produces one, since `classify_title` always returns a member of `MEETING_TYPES` and `set_override` rejects anything else.

A clip name such as "Special Called Finance Committee" classifies as `committee`, `special`, "Finance Committee"; "Regular City Council Meeting" is the generic `council`, `regular`, no body; "Budget Hearing" is `council`, `budget_hearing`. `classify_title` in `_helpers.py` owns these readings.

## The ladder

`services/meeting_types.resolve` classifies one row from the evidence, strongest rung first; the first rung that applies wins and is recorded in `type_source`.

1. **Admin lock.** A row with `type_locked_at` set is returned unchanged; nothing below this rung touches it.
2. **Specific title.** A specific title (one that says special, called, work session, budget, or names a committee or board) is final: the video, the calendar, and the rule never override it.
3. **Video.** For a generic title, a YouTube recording attached to the row (`meeting_videos`) whose cleaned title names a body is final; the council's own name for its stream outranks the calendar and the rule. The row's YouTube clean titles are read primary first, and the first whose `classify_title` is not the generic council reading decides, with `type_source = 'video'` and no calendar event.
4. **Calendar.** For a generic title, the city's calendar events on the meeting's date (America/Chicago) are read (`classify_event`: "CITY COUNCIL MEETING" is a council sitting, special when the title says so; "COMMITTEE" is a committee named by `committee_name_for`, the canonical committee list or the cleaned event title). An event whose stored `event_status` is neither NULL nor `active`, or whose title `query.is_cancelled_title` marks cancelled, is dropped first: a cancelled event names nothing and accounts for nothing. The match reads the row's documents, its stored length (`duration_s`), and the city's other non-hidden rows of the same date (its siblings), and never `start_time`, whose stored values are wrong (issue #88).
   - A row with a minutes link takes the day's council event when exactly one exists, and is never matched to a committee event.
   - A row with agenda items and no minutes link takes the day's council event when exactly one exists, and nothing when the day has several. With no council event it gets nothing on the council's regular weekday: the council's own event can be missing from the stored calendar while a committee's on the same day is there, and the council clip must not be named after that committee (2026-11-03, meeting 3186). On any other weekday it goes on as a row without documents, because the Committee of the Whole and other committee clips carry the next council agenda.
   - A row without documents, on a day with no committee event, takes the council event when that is the day's only event, and nothing otherwise.
   - A row without documents, on a day with exactly one committee event, takes it, unless the row runs under `ELIMINATION_MIN_S` (600 seconds) and a competitor runs 600 seconds or more: a stream test does not share a committee's name with the meeting recorded beside it. A row's competitors are its siblings that also reach this rung as rows without documents by the same test.
   - A row without documents, on a day with several committee events, is named by elimination. A namer is a sibling that the rungs above this one make a `committee` with a body name (by its lock, its specific title, or its recording). Every committee event a namer accounts for is set aside (`same_committee` against `committee_name_for` of the event's title), and the row takes the event left over only when exactly one is left, the row runs at least 600 seconds, and no competitor runs 600 seconds or more or has no stored length. A short competitor does not count; one of unknown length does, since nothing shows it is short. Otherwise there is no match and the day stays generic.

   `same_committee(a, b)` passes each name through `committee_name_for` (which removes an event title's trailing date and the word MEETING, or returns the canonical name), then removes a trailing run of the words "committee", "meeting", and "work session", then reduces to letters; the two are one committee when the results are equal, or when the shorter has at least eight letters and opens the longer ("Committee of the Whole" against the calendar's "COMMITTEE OF THE WHOLE/ADMINISTRATION AND GOVERNMENTAL AFFAIRS COMMITTEE MEETING"). A name with no letters left matches nothing. Who competes and who names is decided from each row's own facts (title, lock, minutes, items, recordings, length), never from what this rung stored for a sibling, so one call per row gives the same answer in any order (decision `0088`). The match writes `calendar_event_id` to the event and, for a committee event, `body_name` from it; a council event names no body.
5. **Schedule rule.** The city's metadata names the council's regular weekday (`council_schedule.weekday`, Monday 0; Birmingham's is Tuesday). A generic-titled row on another weekday, with no minutes link and not cancelled, is a `committee`, `regular` recording with no body name.
6. Otherwise the title's own generic reading stands (`council`, `regular`, source `title`). A row with no `meeting_date` stops at the title rung either way, since the calendar and the rule both need a date.

`resolve_and_store(municipality_id, meeting_ids)` runs after every ingest over the rows the feed listed that day, and after the YouTube pass over the rows it touched. It resolves the rows it was given and, beside them, every non-hidden row of the city on those rows' dates, since one row's new recording or length can change what the calendar rung gives another; each row is resolved once, and the rows whose five columns changed are written in one `UPDATE ... FROM (VALUES ...)` scoped to unlocked rows, so a row that gains minutes, items, or a cancelled title moves back down the ladder on its own. Its count is of rows written, which can exceed the ids given. `clear_override` resolves the unlocked row's whole day the same way. The ingest writers themselves set the four columns from the title on INSERT, and on UPDATE only while `type_source` is `title` and the row is unlocked, so a row the video, the calendar, the rule, or an admin placed keeps its classification while its title, dates, and links still update.

## The label

A reader never sees the clip name as the meeting's name. The Jinja global `meeting_label(meeting)` (registered in `docket.web.create_app`) calls `label_for` in `_helpers.py`: a `council` row reads "City Council meeting", "Special called council meeting", "Council work session", or "Budget hearing" by its sitting; a `committee`, `planning`, or `board` row reads its `body_name`, or "Council committee meeting", "Planning commission meeting", "Board meeting" when none is known, with " (special called)" or " (work session)" appended for those sittings; an `other` row reads its own title. A cancelled title (`query.is_cancelled_title`) appends " (cancelled)", except on an `other` row, which reads its title unchanged. A row without the columns, or with a type outside the vocabulary, prints its title.

The label is the card's heading on the meetings list, the home page's strips, and the city page's "Recent meetings"; it is the meeting page's `h1` and `<title>`. The meeting page's eyebrow carries a chip for `meeting_type` and, when the sitting is not `regular`, a chip reading "special called", "work session", or "budget hearing".

## Provenance

When the label differs from the title, the meeting page prints below the hero the title's source where it is known: `The council's YouTube channel titles this recording “<title>”.` when one of the row's stored recordings has that title as its cleaned title (a `yt-` row the YouTube pass created), `The city's archive lists this recording as “<title>”.` when the row's `source_url` is not on YouTube, and no title sentence otherwise (the 2023 Boutwell rows, whose titles came from the operator's manifest). A row named by the schedule rule continues: "It is not on the council's regular meeting day and the city calendar did not name the body." A row named by the calendar continues: "The city's calendar names it." with a link, "See the event", to the event's `source_url` (`meeting_types.calendar_event_for`). When the name was reached by elimination the sentence is instead "The city's calendar lists more than one committee meeting that day; this is the recording the others do not account for.", with the same link, so the page says how the name was reached (`docs/PRINCIPLES.md`, "Source or silence"). `meeting_types.named_by_elimination(meeting_id)` decides: true only when the row is a `committee` whose `type_source` is `calendar`, its matched event is one `classify_event` reads as a committee, and the city's stored, non-cancelled committee events on that event's Chicago date number more than one. A council row on a day with two committee events keeps the plain sentence, because the test is of the row's own type; the page asks only for a row that has a calendar event. A row named by the `video` rung continues: "The council's YouTube recording names it." with a link, "See the recording", to its first YouTube recording's `url` (`query.videos_for_meeting`, primary first). A row whose label is its title prints nothing.

The same page lists a row's recordings from `meeting_videos`: when a row's own `video_url` is not on YouTube and it has a YouTube recording, the source links gain "Watch on YouTube" (meta "council channel") beside "Watch video"; when it has more than one recording, a line under the links reads "Other recordings of this meeting:" and links each non-primary one as "Part N" (the title's `Pt. N` / `Part N`, `youtube_meetings.part_number`) or "another recording". Each recording attached to a Granicus meeting may also carry a measurement of where it sits on the clip's clock (`meeting_video_alignments`), which the links that open the video at a moment are built from; `docs/specs/video-links.md` describes it, and these links on the meeting page are not timed.

## The filter row

The meetings page at `/al/<slug>/meetings/` carries a `nav.type-filter` above the grid: "All" with the city's visible meeting count, then Council, Committees, Planning, Boards, Other, each linking to `?type=<meeting_type>` with its count from `query.meeting_type_counts` (one `GROUP BY meeting_type` over the city's non-hidden rows). A type with no rows is text, not a link. The filtered page lists only rows of that type.

## The admin override

On a meeting page, an admin sees a form with a `meeting_type` select, a `session_kind` select, and a `body_name` field. Saving posts to `POST /admin/meetings/<id>/type`, which rejects a value outside the vocabularies with 400 and otherwise calls `meeting_types.set_override`: the four columns are written with `type_source = 'admin'`, `type_locked_at = now()`, `type_locked_by` the admin's id, and `calendar_event_id` cleared. A locked row shows "Set by hand on <date>" and an Unlock button posting to `POST /admin/meetings/<id>/type/unlock`, which calls `meeting_types.clear_override`: the lock is cleared and the row is resolved once through the ladder, in one transaction. Neither route clears the row's AI meeting summary; the worker's adoption pass regenerates it as it does after `resolve_and_store`. Both routes redirect to the login page when no admin is signed in, as the other admin POSTs do. The lock survives ingest and the daily resolution until it is lifted.

## The city calendar

The worker task `city_calendar` runs daily (scheduled in `src/docket/worker/scheduler.py`) and, for every active city whose metadata carries `calendar_url`, fills `city_calendar_events` (`municipality_id`, `source_event_id`, `title`, `starts_at`, `ends_at`, `source_url`, `categories`, `event_status`, `fetched_at`; unique on city and source event) through `services/city_calendar.refresh_city_calendar(municipality_id, metadata)`. Three readers run in turn, each named by its own metadata keys (migration 043 wrote Birmingham's), each committing its own events, and each failing alone: a reader that raises is logged and the next one runs, and the refresh raises only when every reader the metadata names failed (decision `0087`).

- **The council page** (`calendar_url`, `https://www.birminghamal.gov/government/city-council`). Its embedded Next.js JSON lists the next four events; `parse_birminghamal_page` reads it, with each title's HTML entities unescaped as a guard (the page's JSON has carried a plain `&` on every read so far; a stored `&amp;` would defeat the committee-name match) and its whitespace collapsed.
- **The events search** (`calendar_search_url`, `https://www.birminghamal.gov/api/search/events`, with `calendar_department_id`, `"55"`). It answers with every upcoming event of the City Council department, ten to a page, and no past event; `fetch_search_events` pages until the total is covered, a page comes back empty, or `SEARCH_MAX_PAGES` (10) is reached. A result that names a department other than `calendar_department` is dropped. The search reports no status.
- **The sitemap** (`calendar_sitemap_url`, `https://www.birminghamal.gov/sitemap.xml`, with `calendar_department`, `"City Council"`). It is the only public listing that still holds past events, and it is how the past calendar is filled. `parse_sitemap` keeps every address whose path begins `/events/` and contains `committee`, `council-meeting`, or `work-session` in any case, newest first by the date that opens the path's last segment. The reader runs last, fetches the event page of each address that is not already a stored `source_url` (the two sides normalised alike by `normalise_event_url`: lower-cased scheme and host, no trailing slash, query, or fragment), at most `SITEMAP_MAX_PAGES` (60) in a run, and `parse_event_page` returns the event only when the page's `department.name` is the city's `calendar_department`. Another department's committee (the Framework Plan Implementation Committee is Planning's) is never stored, so its page is fetched again each day. A page that cannot be fetched is logged and passed over, and three such failures (`SITEMAP_MAX_FAILURES`) end the sitemap read for that run.

Every request of the adapter (`src/docket/adapters/city_calendar.py`) waits until one second has passed since its previous one, and a malformed payload is an empty result and a warning, never an exception. The first run stores the past events the sitemap still lists; a later run fetches only new pages and the few the department test rejects. The task's log line names the count per reader. Not every stored event is a meeting: the department's giveaways and other events are stored like any other, and `classify_event` reads their titles as nothing.

`event_status` is the city's own status for the event: `active` from the council page and the event pages, NULL from the search and on rows stored before migration 043. The upsert writes `COALESCE(new, stored)`, so the search, which runs every morning without a status, does not erase one an event page supplied. No value other than `active` has been observed; the resolver treats anything that is neither NULL nor `active` as cancelled.

Birmingham's metadata also carries `calendar_complete_from` (`"2026-10-05"`), the earliest date from which the sitemap held the council's events when it was first read on 2026-11-11. Events the city had removed from its site before then are not recovered, so a row dated earlier is named by the calendar only if its event was fetched while the council page still listed it, and otherwise by the schedule rule. The hiding rule below treats an empty calendar day as meaningful only from that date.

## The council's YouTube channel

Birmingham's council streams every meeting, council and committee, to its YouTube channel (`metadata.youtube_channel` `citycouncilbham`, `metadata.youtube_channel_id` `UCxKV8MgjDbqw9PMGTsF_NUw`, written by migration 040); most committee meetings never reach Granicus. `services/youtube_meetings.sync_city(slug, client=..., since=..., today=..., dry_run=...)` matches the channel to the city's rows, and is the one entry point for the daily worker task `youtube_ingest` (scheduled in `src/docket/worker/scheduler.py`; uploads of the last `DAILY_WINDOW_DAYS`, 30) and for `scripts/backfill_youtube_meetings.py` (the whole channel). It reads the channel through the YouTube Data API v3 (`src/docket/adapters/youtube.py`, key `YOUTUBE_API_KEY`; decision `0070`); with no key or no channel id it logs a WARNING and reads nothing.

A video is a meeting candidate when `parse_title` finds a date token (`M.D.YY`, `M.D.YYYY`, `/` separators, anywhere in the title; not before 2008 or after tomorrow), a meeting word (`meeting`, `committee`, `council`, `hearing`) and none of the reject words (`highlights`, `recap`, `tease`, `test`, `edition`), the stream has ended, and it runs at least `MIN_RECORDING_S` (300 seconds). The cleaned title is the title without its date and its `Pt. N` / `Part N`; candidates of one date whose `body_key` agrees (lower case, `&` as `and`, without "special called" and "joint", letters only) and whose `classify_title` session kind is alike (special or not) are one group, except that a numbered part (`Pt. N`) joins the group of the other kind when its own has no member, so a stream broken into parts stays one meeting while a special-called meeting beside a regular one does not fold into it. A group's longest video is the primary recording and the rest its parts. A finished upload with a meeting word and no reject word that is left out for want of a readable date or a known duration is not dropped silently: the run logs it and records it as `unparsed` in its report, so the daily task's count line and the backfill's output show it.

For each date, rows an admin has hidden are passed over (logged at INFO), so a recording never attaches to, or is absorbed into, a row a reader cannot see. A group already held in `meeting_videos` is skipped (`skip_seen`), and a held group's new parts join the same row. A council group attaches to the day's council row (among several, the one whose duration pairs, else the one with the most agenda items). A committee group is first tried by name: among the day's visible Granicus rows that hold no YouTube recording, those the calendar already named for the group's committee (`meeting_type = 'committee'`, `type_source = 'calendar'`, and a `body_name` that `meeting_types.same_committee` matches to the group's own; `_named_rows`). Exactly one such row takes the recording whatever either's length, and the report line ends " by name"; among several, the one whose duration pairs takes it (" by name and duration"); with none, or several and no pair, the group goes on to the candidate rule that follows. The step runs once per group in the listing's order, ahead of every candidate rule (the `no_duration` block among them), and a row taken in the run is not offered again. Once attached, the `video` rung outranks the calendar and the row's label becomes the recording's own name. Without this step a recording of a meeting whose clip the calendar had already named would get a `yt-` row of its own, and the meeting would be listed twice. Otherwise a committee group attaches to the day's Granicus candidate row: a committee-typed row with no body name, or a council-typed row with no agenda items and no minutes link beside a council row that has items. One group and one candidate attach; otherwise they pair by duration, the group's total over its parts against the row's `duration_s` (`pairs`: within the larger of 300 seconds and a quarter of the longer; decision `0068`), and the day is listed as ambiguous when any clip or recording is left unpaired. A group with nothing to attach to creates a row `yt-<primary video id>` (title the cleaned title, classification from `classify_title`, `type_source = 'title'`, `video_url` and `source_url` the watch URL, `duration_s` the group's total) once its primary was published at least `CREATE_AFTER_DAYS` (3) days ago, and is deferred until then (decision `0069`); on a date where a committee candidate row has no stored duration, no committee group is attached or created (`no_duration`). Every attached or created recording is a `meeting_videos` row (`provider` `youtube`, the watch URL, the title and cleaned title, duration, stream start, `is_primary` on the primary when the row holds none).

After the groups, absorption: a `yt-` row of the last 30 days with no agenda items, on a date that now has an unmatched Granicus candidate of its kind created after it (one of each, or a duration pair; a clip that was already there when the `yt-` row was created is one the group stage declined, and never absorbs it), has its recordings moved to that row and is deleted, or hidden when a transcript references it (with `hidden_reason = 'absorbed'`), logged at WARNING with both ids. A committee `yt-` row is tried by name first here too: the one visible Granicus clip the calendar named for its committee, created after the `yt-` row, absorbs it (among several, the one whose length pairs), and the report line carries the same note. The writes are one transaction, and `resolve_and_store` then runs over every row attached to, created, or absorbed into, so the `video` rung names them in the same run. A dry run records every decision and writes nothing. A run never updates an existing `yt-` row and skips every video it already holds, so the task and the backfill can be repeated.

## Clips that are not meetings

The clerk's streaming equipment leaves recordings of a minute or a few in Birmingham's Granicus archive on days when no body met, under the same generic title as every real clip. The worker task `non_meetings` (daily, scheduled in `src/docket/worker/scheduler.py` after `youtube_ingest`, so a recording that names a clip is attached first) hides them: `services/non_meetings.hide_non_meetings` sets `is_hidden = TRUE`, `hidden_at = now()`, and `hidden_reason = 'not_a_meeting'`. It is a new writer of `is_hidden` and no new value, so every page, search, the YouTube pass, and the transcriber's claim queries treat such a row exactly as one an admin hid (decision `0089`).

A clip is hidden when all of this holds (`non_meetings.find`):

- the city's metadata carries `calendar_url` and `calendar_complete_from` (Birmingham only);
- the row is visible, not locked by an admin (`type_locked_at IS NULL`), not exempt (`keep_visible_at IS NULL`), and its `external_id` is set and does not begin `yt-`;
- it has no agenda link, no minutes link, no agenda item, and no YouTube recording in `meeting_videos`;
- its `meeting_date` is on or after `calendar_complete_from` and at least `HIDE_AFTER_DAYS` (4) days before today: the YouTube pass creates a row for an unmatched recording at three days, so by four it has attached a recording to the clip, which keeps it, or has none to attach;
- its title is one `classify_title` reads as the generic council reading, and `query.is_cancelled_title` does not mark it cancelled;
- the stored calendar has no event on that date, in America/Chicago, that `classify_event` reads as a council sitting or a committee, whatever the event's status: a cancelled event still keeps the clip, the opposite of the resolver's reading and the safe direction here. An event `classify_event` reads as nothing (a giveaway) keeps nothing;
- it is short, a stored `duration_s` under `SHORT_CLIP_S` (600), or its transcript's status is `low_speech`. A NULL length is not short. Length alone hides nothing, since real committee meetings of six and eleven minutes exist; it is the empty calendar day that marks a test.

Two brakes. While the city's newest `city_calendar_events.fetched_at` is more than `CALENDAR_FRESH_HOURS` (36) hours old by the database's clock, or the city has no stored event, nothing is found and a WARNING is logged: an empty day then means the calendar was not read, not that nothing was scheduled. And a clip that meets every condition but has a public transcript (`uploaded_at` set, status other than `low_speech`) is held back: it is not hidden, and the admin page lists it for the operator to judge.

Two columns from migration 044 carry the record. `meetings.hidden_reason` is `admin` (written by the admin's hide), `absorbed` (the YouTube pass's absorption), `not_a_meeting` (this rule), or NULL on a row hidden before the column existed or not hidden; the CHECK `meetings_hidden_reason_check` admits only those. `meetings.keep_visible_at` is set by an admin's unhide of any row, whatever hid it, and the rule never hides a row that has it; an admin can still hide the row by hand, and nothing in the admin clears the column.

The write is one statement per city, `UPDATE meetings SET is_hidden = TRUE, hidden_at = now(), hidden_reason = 'not_a_meeting' WHERE id = ANY(...) AND is_hidden = FALSE AND keep_visible_at IS NULL` returning the ids it wrote (decision `0026`), so a row an admin hid or exempted between the read and the write is neither written nor reported, and a second run hides nothing new. A city whose read raises is logged and left out. The task logs, per city, the ids hidden and the ids held back.

`scripts/hide_non_meetings.py` runs the same rule by hand for every active city whose metadata carries `calendar_complete_from`: with `--dry-run` it prints one line per clip (id, date, title, `duration_s`, transcript status, and `hide` or `held: has speech`) and writes nothing; without it, it writes and prints the ids hidden.

The admin page `/admin/meetings/hidden` (`list_hidden_meetings` in `src/docket/web/admin.py`) shows each hidden row's reason in words ("by an admin", "merged into another row", "not a meeting: short or silent clip on a day with no calendar event", or blank for a row with none) beside its Unhide button, and below it a second table, "Not hidden: has a transcript with speech", listing every city's held-back clips with a link to each one's meeting page, where the hide button is; it prints "None." when the rule held nothing back. Unhide clears `is_hidden`, `hidden_at`, `hidden_by`, and `hidden_reason` and sets `keep_visible_at`, so a row brought back by hand is never hidden automatically again. To stop the rule for a city without a deploy, remove `calendar_complete_from` from its metadata; to undo every automatic hide, `UPDATE meetings SET is_hidden = FALSE, hidden_at = NULL, hidden_reason = NULL WHERE hidden_reason = 'not_a_meeting'`.

What the rule does not see is listed in `docs/DEBT.md` (`D119`): a short test clip on a day the calendar does list a committee stays visible.

## Reclassifying a city

`scripts/reclassify_meetings.py --city <slug>` resolves every non-hidden row of one city through the ladder, prints the transition table (old type and sitting to new type, sitting, and source, with counts) and, one per line, the rows the schedule rule would classify that predate 2026-01-01, then writes the changed rows in one statement scoped to unlocked rows and clears the AI meeting summary of each row whose body left `council` so the worker regenerates it. The operator runs it one city at a time, `--dry-run` first, against production with `DATABASE_URL` set to `DATABASE_PUBLIC_URL`, reads the pre-2026 list, and locks by hand any row that is a real council meeting before the write (`docs/specs/operations.md` has the Railway pattern). A second dry run after the write prints every count on the diagonal. Birmingham was reclassified on 2026-10-22; on 2026-11-08 the fifteen production rows still outside the vocabulary were all Vestavia Hills' and Homewood's, and those two cities were reclassified that day; Mobile's rows were never passed through the script (the gating query showed none of them outside the vocabulary, and the plan records no count of them). Migration 039's CHECK on `meeting_type` landed after that. On a copy whose rows were never reclassified before 039 applied (a developer copy restored from an older dump), 039's guard UPDATE folds every old-vocabulary value into `other` and leaves `type_source` reading `title`; running the script for each city repairs them, since the resolver reads each title afresh.
